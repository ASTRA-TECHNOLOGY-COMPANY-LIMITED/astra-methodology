ASTRA METHODOLOGY · 개발 참고 문서

Claude 5 세대 프롬프팅 · 하네스 지침 — 무엇을 빼고 무엇을 남기나

"새 모델이 나왔으니 하네스를 다 걷어내라"는 말은 유통 과정에서 과장됐습니다. Anthropic 공식 지침을 직접 읽으면 빼라는 것과 오히려 더하라는 것이 뚜렷하게 갈립니다. 이 문서는 그 경계를 정리하고, astra-methodology에 어떤 함의가 있는지까지 짚습니다.

조사일 2026-08-11 · 대상 모델 Claude Opus 5 · Claude Fable 5 · 1차 출처 Anthropic 공식 프롬프팅 문서 (문서 하단 출처 목록 참조)

1결론 — 하나의 문장이 아니라 두 개의 축

지침은 "지워라" 한 줄이 아닙니다. 지우라는 대상과 만들라는 대상이 서로 다른 층에 있습니다.

빼라 — 규범적 프롬프트 텍스트

모델이 이미 하는 일을 시키는 문장

  • 검증 지시 — "최종 검증 단계를 넣어라", "답하기 전에 다시 확인해라"
  • 압박 언어 — CRITICAL:, MUST, "확신이 없으면 이 도구를 써라"
  • 단계별 안무 — 판단이 필요한 일에 붙인 STEP 1 → STEP 2 스크립트
  • 강제 진행보고 — "도구 3번 호출마다 요약해라"
  • 시스템 프롬프트와 도구 설명에 중복된 같은 규칙
  • 구세대용으로 붙인 회피책 — 서식 교정, 과잉 거부 완화 문구
남기거나 더하라 — 구조적 하네스

코드와 파일이 강제하는 장치

  • 신선한 컨텍스트를 가진 독립 검증자 서브에이전트
  • 도구 결과에 대조하는 진행 보고 규약
  • 메모리 시스템 — 세션을 넘겨 배운 것을 기록할 장소
  • 경계 명시 — 무엇을 하면 안 되는지에 대한 실제 제약
  • 루브릭 · 테스트 스위트 등 기계가 읽는 명세
  • 도구 계약(파라미터 · 실패 모드) 설명 — 오히려 더 자세히

혼선의 출처는 Opus 5 문서의 한 문장입니다. 검증 지시를 지우라고 한 직후에 이렇게 덧붙입니다.

Claude Opus 5 verifies its own work without being told to. If your prompt contains explicit verification instructions … remove them: instructions like these cause over-verification on Claude Opus 5, and removing them reduces wasted tokens with no loss in quality. The same applies to legacy harness scaffolding that adds separate verification steps.

Prompting Claude Opus 5 — Task scope and over-verification

이 마지막 문장만 잘려 나가 "하네스를 지우라"가 됐습니다. 문맥은 검증을 중복시키는 옛 보조 장치를 가리킵니다.

2더하라고 명시된 하네스

Fable 5 문서의 마지막 절 제목이 아예 "Recommended scaffolding changes"입니다. 여기 있는 항목은 전부 빼기가 아니라 더하기입니다.

Make self-verification explicit in long-run prompts. Separate, fresh-context verifier subagents tend to outperform self-critique. For long-running tasks, instruct: Establish a method for checking your own work at an interval of [X] as you build. Run this every [X interval], verifying your work with subagents against the specification.

Prompting Claude Fable 5 — Recommended scaffolding changes

Ground progress claims during long runs. Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that.

Prompting Claude Fable 5 — Ground progress claims during long runs

Anthropic 자체 테스트에서 이 지시가 "허위 상태 보고를 거의 없앴다"고 적혀 있습니다. 같은 문서에 메모리 시스템 구축(Construct a memory system), 경계 명시(State the boundaries), 사용자에게 원문 그대로 전달하는 send_to_user 도구 추가까지 나란히 들어 있습니다.

도구 설명은 방향이 아예 반대입니다. Anthropic의 프롬프트 감사 플레이북은 도구 설명의 기준을 "간결함이 아니라 정확성과 계약 충실도"로 잡고, 가장 흔한 실패가 과소 기술이라고 못박습니다. 최소 3~4문장, 언제 쓰지 말아야 하는지까지 적으라는 쪽입니다.

3검증자 이야기가 모순처럼 보이는 지점

두 문서가 반대로 읽힙니다. Opus 5는 "서브에이전트로 자기 작업을 검증하지 마라"고 하고, Fable 5는 "독립 검증자 서브에이전트가 자기 비평보다 낫다"고 합니다. 대상이 다릅니다.

지우라는 쪽권장하는 쪽
무엇 모델이 재량으로 띄우는 검증 에이전트 하네스가 정해진 시점에 호출하는 검증 게이트
누가 부르나 프롬프트 문장을 읽은 모델 스킬 · 파이프라인 코드
언제 아무 때나 — 몇 번의 도구 호출로 끝날 일에도 장기 작업의 정해진 마일스톤
문제 / 효과 비용과 지연이 배로 늘어남 신선한 컨텍스트라 자기 비평보다 결함을 잘 찾음

Opus 5는 예전 모델보다 서브에이전트를 훨씬 쉽게 띄웁니다. 그래서 프롬프트에 "검증용 서브에이전트를 써라"라고 적어두면 안 됩니다. 반대로 코드가 부르는 게이트는 그대로 두는 게 맞습니다.

실무 판별 기준 검증을 문장으로 시키고 있다면 지우기 후보, 코드가 호출하고 결과를 기계 판독으로 판정한다면 유지 대상입니다.

4"시스템 프롬프트 80% 삭제"의 실체

Anthropic 기술직원 Thariq Shihipar가 2026년 7월 말 공개한 내용입니다. Claude Code 시스템 프롬프트를 Opus 5 · Fable 5 대상으로 80% 이상 걷어냈고 자체 코딩 평가에서 측정 가능한 손실이 없었다는 것. 2차 소스가 보고한 수치는 약 2,686단어 → 약 514단어(메모리를 끈 상태)이고, 메모리를 켜면 약 830단어라 감소폭이 70%쯤으로 줄어듭니다.

발표 형식과 귀속은 2차 소스마다 갈립니다 — X 포스트인지 AI Engineer World's Fair 발표인지, Thariq인지 Boris Cherny인지. 원문 링크 기준으로는 Thariq의 X 포스트입니다.

여섯 가지 전환

전환지운 것대신 둔 것
규칙 → 판단"여러 문단짜리 독스트링을 절대 쓰지 마라""주변 코드처럼 써라 — 주석 밀도, 명명, 관용을 맞춰라"
예시 → 인터페이스 설계정확한 API 호출을 보여주는 도구 사용 예시표현력 있는 스키마 — 상태 열거형, 타입 지정 필드
사전 로딩 → 점진적 공개시스템 프롬프트에 박아둔 검증 절차 · 코드 리뷰 규칙스킬과 지연 로딩 도구로 필요할 때만
반복 → 통합시스템 프롬프트와 도구 설명의 중복 지시도구 설명이 단일 출처, 시스템 프롬프트는 참조만
수동 → 자동 메모리단축키와 CLAUDE.md 수기 관리자동 저장 — 메모리를 하네스 인프라로 취급
평문 명세 → 풍부한 참조계획과 명세를 담은 마크다운 파일HTML 산출물, 코드 명세, 테스트 스위트, 루브릭

여섯 번째 항목을 눈여겨볼 만합니다. 루브릭 기반 검증은 격하가 아니라 오히려 격상됐습니다.

삭제 진영이 스스로 붙인 경고 "손실 없음"은 Anthropic의 코딩 평가 기준이지 당신 제품의 평가 기준이 아닙니다. 규제 환경(SOC 2 · HIPAA · PCI-DSS)의 프로덕션 에이전트는 제약을 줄이는 게 아니라 늘려야 하고, 결정론적 동작을 판단 기반 프롬프트로는 보장할 수 없습니다. 이 축소는 Opus 5 · Fable 5 전용이라 구세대 모델은 기존 프롬프트를 그대로 씁니다 — 여러 모델을 지원하는 하네스라면 프로필이 둘 필요합니다.

참고로 "6개월마다 CLAUDE.md · 스킬 · 훅을 지워라"나 Vercel의 "도구 80% 제거로 성공률 80→100%" 같은 이야기는 검색 스니펫에만 있는 미검증 2차 주장입니다. 1차 확인 없이 인용하지 않는 편이 낫습니다.

5지우면 안 되는 것 — Anthropic 자체 감사 규칙

Anthropic이 별도로 제공하는 프롬프트 감사 플레이북(/claude-api prompt-audit)에는 keep list가 명시돼 있습니다. 균형점을 가장 잘 보여주는 대목입니다.

  • 맥락은 절대 군더더기가 아니다. 대상 사용자, 제품, 환경 사실, 품질 기준, 그리고 제약의 이유 — 작성자만 아는 것은 남긴다.
  • 군더더기 ≠ 길이. 글자 수만으로 삭제를 정당화하지 않는다. 해악은 분량이 아니라 특정 시대착오적 지시에서 나온다.
  • 위험한 작업은 정확한 스크립트를 유지한다. 파괴적 명령, 인증 흐름, 컴플라이언스 절차처럼 안전한 순서가 하나뿐인 곳.
  • 현재 모델에서 실제로 재현되는 실패를 막는 금지 규칙은 남긴다. 판별 기준은 "금지문처럼 생겼나"가 아니라 "그 실패가 지금도 나는가".
  • 감사에서 아무것도 안 나왔으면 아무것도 바꾸지 않는다. 빈 diff가 억지 diff보다 낫다.
  • 재조정은 추가를 뜻하기도 한다. 새 모델의 새로운 실패 모드에는 오히려 지침을 더해야 한다.

플레이북은 검증 절차 자체도 규정합니다 — 삭제는 결론이 아니라 가설이라, 사본에서 행동 기반 검사를 전후로 돌려보고 판단하라는 것. 모델에게 "이 지시가 필요하냐"고 물어보는 건 측정이 아닙니다.

6astra-methodology에 대한 함의

구조는 새 지침과 부딪히지 않습니다. loop-verifier와 screen-verifier는 스킬이 정해진 시점에 호출하는 신선한 컨텍스트 검증자이고, 고정 루브릭과 기계 판독 계약 라인(ASTRA_TEST_RESULT: 계열)은 여섯 번째 전환이 가리키는 "평문 명세 → 루브릭" 방향과 같습니다. verify-before-claim 규약의 근거(모델이 완료를 과신 — 예측 73% 대 실제 35%)는 Fable 5 문서의 "진행 보고 전에 각 주장을 이번 세션의 도구 결과에 대조하라"와 같은 문제의식입니다.

감사 대상은 구조가 아니라 SKILL.md 안의 산문입니다.

  • 판단이 필요한 구간에 붙은 단계별 안무 — 순서가 실제로 중요한 곳만 남기고 결과·제약·검증법 서술로 바꾼다
  • CRITICAL: · MUST 같은 압박 언어 — 근거가 붙은 한두 개만 남긴다
  • 시스템 프롬프트 격 문서와 도구/에이전트 설명 사이의 중복 지시
  • "완료 전에 다시 확인하라" 식 자기 점검 문장 — 모델이 이미 하는 일
일괄 삭제가 아니라 평가 기반 감사 이 플러그인을 쓰는 사람이 구세대 모델을 돌릴 수 있습니다. Opus 5 · Fable 5 기준으로 걷어낸 문장이 Opus 4.x 사용자에게는 여전히 필요할 수 있으니, 삭제 전에 대상 모델을 정하고 자체 평가로 확인하는 절차가 필요합니다.

바로 돌릴 수 있는 도구가 있습니다. /claude-api prompt-audit는 프롬프트 · 스킬 · 도구 설명을 훑어 file:line 단위 감사 보고서와 제안 diff를 내주고, 파일은 건드리지 않습니다. 명시적으로 적용을 요청하지 않는 한 읽기 전용입니다.
