# ASTRA v4.x → v5.12.0 Changelog

Version-change rationale moved out of CLAUDE.md (which is loaded every session) to keep the session context lean. Newest first.

> **v5.11.2 → v5.12.0 change (/loop convergence loop)**: new `/loop` skill + `loop-verifier` agent implement the evaluator-optimizer pattern for open-ended targets that don't fit the fixed `/autorun` pipeline. The design encodes three external best practices on top of ASTRA house patterns: (1) **max iterations is the safety mechanism; the score is only a success signal** (Ralph-loop lesson) — so Stage 0.5 asks the max iteration count via `AskUserQuestion` on EVERY invocation, even when `--max-iter=N` is passed (the argument only pre-selects an option, it never skips the question); (2) **LLM-judge leniency bias** (scores cluster near the top of the scale) — mitigated by a triple exit gate (objective test-runner exit 0 ∧ score ≥ 90 ∧ P0 == 0), additive-from-0 scoring with mandatory file:line evidence per criterion, and a rubric frozen at Stage 0.3 (HITL-confirmed, immutable mid-loop; presets A–E live in `skills/loop/references/rubric-template.md`); (3) **fresh-context adversarial verification** — the read-only `loop-verifier` (sonnet, refute-first mandate) judges artifacts only, never the worker's rationale, and emits the machine-parseable `ASTRA_LOOP_RESULT: score=N verdict=PASS|FAIL p0=N iter=I` tail line (same contract style as `ASTRA_REVIEW_RESULT`; the PASS threshold ≥ 90 is deliberately stricter than the reviewers' ≥ 80 because this line terminates an autonomous loop). Loop exits: early exit on PASS, hard stop at max iterations, stall stop (2 consecutive non-improving scores → HITL continue/stop). A failing objective gate short-circuits the verifier for that iteration (saves a sub-agent run; the test failure list becomes the next iteration's fix directives). Reuses the autorun state-file protocol (`astra_state_*` with explicit scope `loop-{slug}`) and the ≤ 200-line iteration-summary handoff rule. `/loop` performs no commit/PR/merge — it converges the working tree and hands off to `/pr-merge` or manual git flow. New agent-naming class registered: `*-verifier` (adversarial loop-gate scoring, skill-invoked only).

> **v5.11.1 → v5.11.2 change (promotion target always HITL under `--auto`)**: `/pr-merge` Step 8.4.5.1 (the post-merge promotion-path prompt — `dev` / `staging` / `skip`) **now always fires `AskUserQuestion`, even under `--auto`**. Previously, `--auto` silently picked `dev` (standard path); the user feedback was that the merge target branch where the integration branch finally lands is a deployment-surface decision with no safe unattended default — silently promoting to `dev` (or to `staging` if a different default had been chosen) can both trigger unintended downstream effects. The prompt is the same as in normal mode (dev recommended first, staging fast path, skip defer). `/autorun` and `/sprint-init --auto` now treat this as a routine HITL pause — the pipeline still completes end-to-end in a single invocation, but the user must pick the target. Direct integration → `main` is intentionally NOT offered here; the explicit `/pr-merge --main` promotion remains the only path to production (which includes the version bump and release checks). All other `--auto` behaviors (commit confirmation, final-merge confirmation, integration-branch auto-pick in Step 4.5, base auto-pick in Step 4.5.4, promotion-mode source defaults in Step 10.0) are unchanged.

> **v5.11.0 → v5.11.1 change (integration-branch promotion)**: `/pr-merge --staging` and `/pr-merge --main` promotion modes now ask the user to pick the source in a new **Step 10.0** — the legacy bulk source (`dev` for `--staging`, `staging` for `--main`) is still the default and still runs Step 8 code review on the accumulated diff, but the user can alternatively pick a specific integration branch (`feat/<name>` or `fix/<name>`) from the top-3 most-recent list to perform feature-level promotion that skips Step 8 (sprint PRs already reviewed). This closes the hotfix path end-to-end: a single feature can travel sprint→integration (Step 8.4.5 staging-direct option) and then integration→main (--main with integration source) without ever entering bulk dev/staging promotion. Step 10.1 PR body branches on source type so the reviewer can tell whether a fresh review ran on this PR or was inherited from the source sprint PRs. Empty integration-branch list falls back to bulk default (no AskUserQuestion failure). Under `--auto`, both promotion modes default to legacy bulk sources, preserving the existing unattended behavior.

> **v5.10 → v5.11 change (integration-branch model)**: `/pr-merge` no longer targets `dev` directly. Sprint PRs (`head=feat/sprint-*`) target an **integration branch** (`feat/<name>` or `fix/<name>`) chosen interactively in the new **Step 4.5**: the user picks from existing integration branches (top 3 by recent activity) or creates a new one with a user-chosen base (default `origin/dev`; can also be `origin/staging` / `origin/main` / `origin/master` / custom). Classification (feat vs fix) and the slug are auto-inferred from commit prefixes, the sprint slug, and the blueprint, then surfaced for confirmation. After the sprint PR merges into the integration branch, the new **Step 8.4.5** asks the promotion path — `staging` (fast hotfix), `dev` (standard, recommended first option), or `skip` — and creates a promotion PR (no fresh code review; the sprint PR already passed). Integration branches are **persistent** — Step 9 explicitly protects them from `git branch -d`. `/sprint-init` Step 1.5 also became interactive: the source branch (where the sprint worktree branches from) is chosen by the user (`dev` default, also `staging`/`main`/`master`/custom). Under `--auto`, most new prompts default to safe values (reuse existing integration branch if name matches else create from dev; sprint source = dev) so `/autorun` and `/sprint-init --auto` still complete end-to-end — **with one exception: the Step 8.4.5 promotion-target prompt always fires, even under `--auto`** (v5.11.2+), because the deployment surface (dev vs. staging vs. skip) has no safe unattended default. Backward compat: Step 3.5 falls back to the legacy `base=dev` filter when no integration-base PR is found, so pre-v5.11 sprint PRs continue to merge. Step 3.5 query: `gh pr list --state open --jq '.[] | select(.headRefName | test("^feat/sprint-")) | select(.baseRefName | test("^(feat|fix)/"))'`.

> **v5.9 → v5.10 change (worktree-first blueprint)**: `/blueprint` now runs in a **worktree-first order**. Instead of authoring the blueprint on dev (in the main worktree) and then auto-creating a sprint worktree at the end (v5.8/5.9 Step 6.5), the new flow is: (1) determine blueprint directory number on the main worktree, (2) delegate to `/sprint-init --scaffold-only` (new flag) to create the sprint worktree + write `.astra-worktree.env` + scaffold prompt-map / progress / retrospective, (3) cd into the worktree, (4) author the blueprint *inside* the worktree, (5) blueprint-reviewer, (6) commit on the sprint branch. The `--scaffold-only` flag suppresses Feature 1.1 (blueprint authoring) from the prompt-map and renumbers the remaining steps (1.1 = DB Design, 1.2 = Test Cases, 1.3 = Implementation). The non-standard-branch case became an **error abort** (previously a warning + skip) — every successful `/blueprint` invocation guarantees a sprint worktree exists or is reused. This removes the "dev visibility guarantee" logic of v5.8/5.9 (cross-branch commit timing race) — the blueprint reaches `dev` only via `/pr-merge` at sprint end. `/autorun` Stage 3 unchanged in behavior since `/blueprint` already does the worktree creation; Stage 4 (`/sprint-init` re-entry) remains an idempotent guard. The `--from-blueprint` flag on `/sprint-init` is preserved as a backward-compat alias for `--scaffold-only`.

> **v5.8 → v5.9 change**: `/pr-merge` now follows a two-phase policy. The destructive merge step (`gh pr merge`) only runs from the main worktree, so accidental cross-worktree side effects are minimized and the merge action is reviewable from the same cwd that holds dev/staging/main. Sprint Phase (commit → PR → review → fix) still runs inside the sprint worktree as before, but exits after the review loop and prints a `cd` command. Main Phase, triggered by re-invoking `/pr-merge` from the main worktree, auto-detects the pending sprint PR (`base=dev`, `head=feat/sprint-*`) and finalizes the merge + worktree removal. `--auto` chains both phases automatically — `/autorun` and `/sprint-init --auto` continue to complete end-to-end in a single invocation. When multiple pending sprint PRs are detected on Main Phase entry, `AskUserQuestion` is preserved even under `--auto` (picking the wrong PR is destructive). Promotion modes (`--staging`, `--main`) are unaffected — they remain main-worktree-only and merge in-place.

> **v5.7 → v5.8 change**: `/blueprint` now auto-creates the sprint worktree at the end of authoring (Step 6.5). This removes the manual `/sprint-init` step from the recommended workflow but is fully backward compatible — `/sprint-init` direct invocations still work, and `/blueprint` skips worktree creation when already inside a sprint worktree or on a non-standard branch. `/autorun` Stage 4 (sprint plan) became an idempotent re-entry that skips when the worktree is already present.

> **v5.9.0 addition (/user-test)**: AI-assisted UAT skill for end-user flows. Drives Chrome MCP with hard-assertion verification (URL / Network / DOM / Console) and auto-assigns severity (CRITICAL/HIGH/MEDIUM/LOW) per a fixed rule table in `references/assertion-guide.md`. Interactive mode (URL + natural-language flow → draft test case) and `--auto` mode (batch-runs `docs/tests/uat-cases/`, filterable by `--priority`/`--feature`/`--from`). Output: timestamped `docs/tests/uat-reports/{YYYY-MM-DD-HHmm}/` with `index.html`, `issues.md` (failures only), `session.json`. On FAIL the case is skipped and the run continues. Distinct from `/test-run` (developer integration tests) and `/test-scenario` (scenario authoring). No GitHub Issue integration — local `issues.md` only.

> **v5.6 → v5.7 change (/tool-author)**: new skill that authors and validates runtime LLM tool descriptions and input schemas (Anthropic Tool Use, MCP `server.tool()`, LangChain `@tool`, Pydantic, Zod). Enforces six required attributes (one-line summary, anti-pattern, synonyms, parameter examples, enum constraints, return shape) and blocks seven failure modes (wrong-tool selection, skipped tool, malformed arguments, retry loops, user-intent bypass, wrong side-effect, un-auditable traces). Auto-triggers on `tools/**`, `mcp/**`, `**/tools.py`, `src/**/*.tool.ts`. Scoped to runtime tool surfaces — `/skill-author` remains the entry point for ASTRA SKILL.md files.

> **v5.5 → v5.6 change**: `/pr-merge` cascade merge restricted to `staging → dev` only — `main → staging` is no longer auto-cascaded; `main` is touched only via the explicit `--main` promotion. Promotion modes (`--staging`, `--main`) skip the cascade entirely. Training docs (branch-strategy 1pager / ko / vi) and CLAUDE.md updated for the single-hop cascade flow.

> **v5.4 → v5.5 change (English localization)**: full English localization of plugin internals (skills, commands, agents, hooks, scripts, docs, CLAUDE.md). Skill description language policy now mandates English for all skills (auto-trigger accuracy + consistency). Runtime end-user output language remains controlled by `/select-language` (Korean / Vietnamese / English). Korean public-data dictionary terms, prefixes/suffixes (`TB_`, `_YMD`, etc.), and dictionary field names (`공통표준용어명`, etc.) are preserved as data definitions.

> **v5.3 → v5.4 change (DESIGN.md SSoT)**: design-system SSoT consolidated into `docs/design-system/DESIGN.md` (Google Stitch + ASTRA 3-tier hybrid). Four new skills/commands — `/design-init` (generates DESIGN.md + regenerates `src/styles/design-tokens.css`), `/design-extract` (OKLCH token extraction from image/PDF/URL references), `/design-redesign` (audit + P0 auto-fix against DESIGN.md), `/design-audit` (lightweight token-violation report). `design-token-validator` treats DESIGN.md as SSoT and design-tokens.css as a generated artifact. `/service-planner` Step E loads DESIGN.md first; `/handoff-publish` 6-component-specs.md references DESIGN.md §4. New PostToolUse hook `notify-design-md.sh` (throttled, non-blocking). `/project-init` bootstraps DESIGN.md during Sprint 0.

> **v5.2 → v5.3 change (MCP reorganization)**: `fect-slack` removed from plugin-required MCPs (still consumed by `/slack-import`, `/extract-backlog`, `/sprint-progress` via user-scope registration); `fect-image` (Gemini, `GOOGLE_API_KEY`) and `fect-gpt-image` (OpenAI gpt-image-2, `OPENAI_API_KEY`) added for `/catalog-generator` image generation; `chrome-devtools` (chrome-devtools-mcp@latest) added as a first-class required MCP for `/manual-generator`, `/catalog-generator`, and `/test-run`. SessionStart hook reports API-key availability.

> **v5.1 → v5.2 change (Silent Save Protocol)**: `/sprint-init --auto` writes `auto-state.yaml` + commits between stages and continues directly to the next stage (no exit, no user `--resume`). A 'reference-avoidance' rule stops the LLM from re-reading large prior artifacts so built-in auto-compression keeps context manageable. `--resume` reserved for true recovery (context crash, forced interrupt). Replaces the prior 'exit + `/compact` + `--resume`' pattern.

> **v5.0 → v5.1 change (/blueprint skill)**: dedicated blueprint-authoring skill — 10 standard sections (data flow, schema DDL, API contract, sequence diagrams, pseudocode logic; no executable code) plus Section 10 'HITL Triggers' consulted by `/feature-dev` during implementation (T1 business decisions, T2 security/permission, T3 external dependency, T4 destructive changes). Replaces inline blueprint authoring in `/sprint-init` prompt-map Step 1.1 and `/autorun` Stage 3.

> **v4.x → v5.0 breaking changes**: the `/pr-merge --start <branch>` mode has been removed. `/test-run` no longer performs dev merge/push (that role moved to `/pr-merge`), and the post-merge "dev→staging auto-promotion" prompt was removed. The main-worktree guards on `test-scenario`/`test-run` were lifted.
