## 1. 마이크로 인터랙션 (Micro-interactions)

마이크로 인터랙션은 단일 작업을 중심으로 하는 작고 정밀한 순간적 인터랙션이다. 트리거(Trigger) → 규칙(Rules) → 피드백(Feedback) → 루프/모드(Loops & Modes)의 4단계 구조로 구성된다 (Dan Saffer, 2013).

### 1.1 버튼 피드백 (Button Feedback / 버튼 반응)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자가 버튼을 누를 때 시각적·촉각적 반응을 제공하는 패턴. 눌림 효과(scale down), 색상 변화, ripple effect 등이 포함된다. |
| **UX 원칙** | **피드백 원칙 (Feedback Principle)** — 시스템은 사용자의 모든 행동에 즉각적인 반응을 보여야 한다. 100ms 이내의 반응은 "즉각적"으로 인식된다 (Jakob Nielsen). |
| **플랫폼** | Both (Web + Mobile) |
| **구현 복잡도** | Low |
| **실제 사례** | Material Design의 Ripple Effect (Google 전 제품군), iOS의 버튼 highlight state, Stripe의 버튼 로딩 애니메이션 |

**구현 팁:**
- `transform: scale(0.95)`와 `transition: 150ms ease`를 결합하여 자연스러운 눌림 효과 구현
- `:active` pseudo-class에 시각 변화 적용, `:focus-visible`에는 포커스 링 유지
- 모바일에서는 `touch-action: manipulation`으로 300ms 탭 딜레이 제거
- 비활성 버튼에는 `opacity: 0.4` + `pointer-events: none` 적용

### 1.2 토글 애니메이션 (Toggle Animation / 토글 전환)

| 항목 | 내용 |
|------|------|
| **설명** | ON/OFF 상태 전환 시 슬라이드, 색상 변화, 아이콘 모핑 등의 애니메이션으로 상태 변화를 명확히 전달하는 패턴. |
| **UX 원칙** | **가시성 원칙 (Visibility of System Status)** — Nielsen의 10가지 휴리스틱 중 1번. 현재 상태를 사용자에게 항상 알려야 한다. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | iOS Settings 토글 (green slide), Android Material Switch, Slack의 알림 토글 |

**구현 팁:**
- 토글 전환 시간은 200~300ms가 적정 (너무 빠르면 인지 불가, 너무 느리면 답답함)
- 색상만으로 상태를 구분하지 말 것 — 아이콘(체크마크/X)이나 텍스트 라벨 병행 (색각 이상 대응)
- `prefers-reduced-motion` 미디어 쿼리로 모션 감소 설정 대응
- 토글 변경 시 서버 동기화가 필요하면 낙관적 업데이트(Optimistic Update) 적용

### 1.3 로딩 상태 (Loading States / 로딩 상태 표시)

| 항목 | 내용 |
|------|------|
| **설명** | 데이터 로딩 중임을 사용자에게 알리는 시각적 표현. 스피너, 프로그레스 바, 스켈레톤 UI, 시머 효과 등 다양한 형태가 있다. |
| **UX 원칙** | **도허티 임계값 (Doherty Threshold)** — 시스템 응답이 400ms 이내일 때 생산성이 급격히 향상된다. 그 이상 걸릴 경우 진행 피드백이 필수. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Facebook/LinkedIn의 Skeleton Screen, YouTube의 시머 로딩, Notion의 페이지 로딩 애니메이션 |

**구현 팁:**
- 0~100ms: 피드백 불필요 / 100~400ms: 간단한 인디케이터 / 400ms~1s: 스피너 / 1s 이상: 프로그레스 바 or 스켈레톤
- 스켈레톤 UI는 실제 콘텐츠 레이아웃과 동일한 형태로 만들어 인지 부하 감소
- 시머 효과는 왼쪽→오른쪽 gradient 애니메이션으로 "살아있음"을 전달
- 무한 스피너 대신 예상 시간 또는 단계별 메시지 표시 (예: "데이터를 분석하고 있습니다...")

### 1.4 당겨서 새로고침 (Pull-to-Refresh / 당겨서 새로고침)

| 항목 | 내용 |
|------|------|
| **설명** | 리스트 최상단에서 아래로 당기면 콘텐츠가 새로고침되는 모바일 네이티브 패턴. Loren Brichter가 Tweetie 앱에서 최초 발명(2008). |
| **UX 원칙** | **직접 조작 원칙 (Direct Manipulation)** — 사용자가 인터페이스 객체를 직접 조작하는 느낌을 제공하면 학습 비용이 낮아진다 (Ben Shneiderman). |
| **플랫폼** | Mobile (Web에서는 제한적) |
| **구현 복잡도** | Medium |
| **실제 사례** | Twitter/X의 pull-to-refresh, Instagram 피드, Gmail 받은편지함, 네이버 앱 |

**구현 팁:**
- 당김 거리에 비례하는 시각 피드백 제공 (아이콘 회전, 진행률 표시)
- 임계값(threshold) 도달 전 놓으면 원위치 복귀, 도달 후 놓으면 새로고침 실행
- 새로고침 완료 후 최소 300ms 지연으로 "완료되었음"을 인지할 시간 확보
- 웹에서는 `overscroll-behavior: contain`으로 브라우저 기본 동작 방지

### 1.5 좋아요/하트 애니메이션 (Like/Heart Animation / 좋아요 반응)

| 항목 | 내용 |
|------|------|
| **설명** | 좋아요·하트 버튼을 누를 때 파티클 폭발, 크기 변화, 색상 채움 등의 풍부한 애니메이션으로 감정적 만족감을 제공하는 패턴. |
| **UX 원칙** | **감성 디자인 (Emotional Design)** — Don Norman의 3단계 디자인 중 "본능적(Visceral)" 수준. 즉각적인 감각적 반응이 긍정적 감정을 유발한다. **가변 보상 (Variable Reward)** — 매번 미묘하게 다른 애니메이션이 도파민 반응을 촉진한다. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Twitter/X의 하트 폭발 애니메이션, Instagram 더블탭 하트, Medium의 Clap 카운터, 카카오스토리 좋아요 |

**구현 팁:**
- Lottie 또는 CSS keyframe으로 구현 (SVG path morphing + scale + opacity)
- 애니메이션 지속 시간은 300~600ms가 이상적 — 너무 짧으면 못 보고, 너무 길면 반복 시 방해
- 모바일에서 더블탭 좋아요는 피드 이미지 중앙에 큰 하트 오버레이로 구현
- 취소(unlike) 시에는 화려한 애니메이션 없이 조용히 처리 (비대칭 피드백)

### 1.6 카운터 애니메이션 (Counter Animation / 숫자 변화 효과)

| 항목 | 내용 |
|------|------|
| **설명** | 숫자가 변경될 때 롤링(odometer), 슬라이드, 페이드 등의 애니메이션으로 변화를 강조하는 패턴. |
| **UX 원칙** | **변화 맹시 방지 (Change Blindness Prevention)** — 인간은 점진적 변화를 놓치기 쉬우므로 변화 순간에 시각적 강조가 필요하다. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Robinhood 주가 변동, 토스 자산 현황, GitHub 스타 카운터, 쿠팡 장바구니 뱃지 |

**구현 팁:**
- 숫자 증가/감소 방향에 따라 위→아래 또는 아래→위 슬라이드 적용
- `requestAnimationFrame`으로 부드러운 숫자 카운팅 구현
- 큰 숫자 변화는 easing(ease-out)으로 점진적 감속 효과 적용
- 가격, 포인트 등 금전 관련 숫자는 천 단위 구분자와 함께 애니메이션

## 2. 내비게이션 패턴 (Navigation Patterns)

내비게이션은 사용자가 앱 내에서 목적지를 찾고 이동하는 방식을 결정한다. 좋은 내비게이션은 "투명"해야 한다 — 사용자가 내비게이션 자체를 의식하지 않고 콘텐츠에 집중할 수 있어야 한다.

### 2.1 탭 바 (Tab Bar / 하단 탭 내비게이션)

| 항목 | 내용 |
|------|------|
| **설명** | 화면 하단에 3~5개의 주요 섹션을 아이콘+라벨로 배치하는 최상위 내비게이션 패턴. iOS Human Interface Guidelines와 Material Design 모두 권장하는 표준 패턴. |
| **UX 원칙** | **피츠의 법칙 (Fitts's Law)** — 타겟이 크고 가까울수록 빠르게 접근할 수 있다. 하단 탭은 엄지 도달 범위(thumb zone) 내에 위치하여 조작이 용이하다. **밀러의 법칙 (Miller's Law)** — 인간의 작업 기억은 7±2개 항목. 탭은 5개 이하로 제한해야 한다. |
| **플랫폼** | Mobile (Web에서는 상단 탭 변형) |
| **구현 복잡도** | Low |
| **실제 사례** | Instagram (홈/검색/릴스/쇼핑/프로필), 카카오톡 (친구/채팅/뷰/쇼핑/더보기), YouTube, 토스 |

**구현 팁:**
- 최소 터치 타겟 48x48dp (Material) 또는 44x44pt (iOS HIG) 준수
- 활성 탭은 색상 + 아이콘 변화(filled/outlined)로 명확히 구분
- 알림 뱃지는 최소 크기로 표시하되 접근성을 위해 `aria-label`에 카운트 포함
- 탭 전환 시 상태 보존 — 각 탭의 스크롤 위치, 입력 상태 유지

### 2.2 햄버거 메뉴 (Hamburger Menu / 숨김 내비게이션)

| 항목 | 내용 |
|------|------|
| **설명** | 세 줄 아이콘(☰) 뒤에 내비게이션 메뉴를 숨기는 패턴. 화면 공간을 절약하지만 발견 가능성(discoverability)이 낮다. |
| **UX 원칙** | **인지 부하 이론 (Cognitive Load Theory)** — 정보를 숨겨 화면을 단순화하지만, **보이지 않으면 존재하지 않는 것 (Out of Sight, Out of Mind)** 원칙과 충돌한다. NNGroup 연구에서 숨김 메뉴는 탐색 빈도가 낮아지는 것으로 확인되었다. |
| **플랫폼** | Both (모바일 우선, 데스크톱에서는 보조적) |
| **구현 복잡도** | Low |
| **실제 사례** | Gmail (모바일), Spotify (과거→현재 탭 바로 전환), Facebook (과거→현재 탭 바로 전환) |

**구현 팁:**
- 주요 기능은 탭 바에 노출하고 부차적 기능만 햄버거 메뉴에 배치
- 메뉴 열림 시 오버레이(scrim) + 스와이프로 닫기 지원
- 메뉴 항목에 아이콘 병행으로 스캔 속도 향상
- 웹에서는 768px 이상에서 사이드바로 확장, 그 이하에서 햄버거로 축소

### 2.3 제스처 내비게이션 (Gesture Navigation / 제스처 기반 이동)

| 항목 | 내용 |
|------|------|
| **설명** | 스와이프, 엣지 제스처 등 터치 동작으로 화면 간 이동하는 패턴. iOS에서 좌측 가장자리 스와이프로 뒤로 가기, Android의 시스템 제스처 내비게이션 등. |
| **UX 원칙** | **직접 조작 (Direct Manipulation)** + **야콥의 법칙 (Jakob's Law)** — 사용자는 다른 앱에서 배운 제스처를 동일하게 기대한다. OS 수준의 제스처 규약을 따라야 학습 비용이 최소화된다. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Medium |
| **실제 사례** | iOS 시스템 뒤로 가기(edge swipe), Android 10+ 제스처 내비게이션, Tinder 스와이프, Safari 탭 전환 |

**구현 팁:**
- 플랫폼 기본 제스처(뒤로 가기, 홈 등)와 충돌하지 않도록 주의
- 제스처 시작 시 시각적 힌트 제공 (페이지 모서리 그림자, 미리보기)
- 제스처 중간에 손가락을 떼면 임계값 기준으로 완료/취소 결정
- 제스처가 유일한 조작 방법이 되지 않도록 버튼 대안 항상 제공 (접근성)

### 2.4 브레드크럼 (Breadcrumbs / 경로 탐색)

| 항목 | 내용 |
|------|------|
| **설명** | 현재 페이지의 계층적 위치를 경로 형태(홈 > 카테고리 > 서브카테고리 > 현재)로 보여주는 보조 내비게이션. |
| **UX 원칙** | **인지 지도 (Cognitive Map)** — 사용자가 정보 공간 내 자신의 위치를 파악할 수 있게 해준다. **헨젤과 그레텔 효과** — 왔던 길을 되짚을 수 있다는 안정감 제공. |
| **플랫폼** | Web (모바일에서는 공간 제약으로 제한적) |
| **구현 복잡도** | Low |
| **실제 사례** | Amazon 상품 카테고리, Google 검색 결과, Notion 페이지 경로, Jira 이슈 경로 |

**구현 팁:**
- 마지막 항목(현재 페이지)은 링크가 아닌 일반 텍스트로 표시
- `<nav aria-label="Breadcrumb">` + `<ol>` 시맨틱 마크업 사용
- 구조화 데이터(Schema.org BreadcrumbList) 추가로 SEO 향상
- 모바일에서는 "< 상위 카테고리" 형태의 단일 뒤로가기 링크로 대체

### 2.5 바텀 시트 (Bottom Sheet / 하단 시트)

| 항목 | 내용 |
|------|------|
| **설명** | 화면 하단에서 올라오는 모달 패널. 추가 옵션, 상세 정보, 필터 등을 맥락을 유지하면서 보여주는 패턴. |
| **UX 원칙** | **맥락 보존 (Context Preservation)** — 전체 페이지 전환 없이 추가 정보를 제공하여 사용자의 작업 흐름을 방해하지 않는다. **피츠의 법칙** — 하단에서 올라오므로 엄지 도달 범위 내에서 조작 가능. |
| **플랫폼** | Mobile (Web에서는 모달/사이드 패널 변형) |
| **구현 복잡도** | Medium |
| **실제 사례** | Google Maps 장소 상세, Apple Maps, Uber 승차 정보, 카카오맵, 토스 결제 시트 |

**구현 팁:**
- 3단계 높이 지원: peek(미리보기), half(절반), full(전체화면)
- 드래그 핸들(grab bar) 상단에 배치하여 드래그 가능함을 시각적으로 암시
- 배경 스크림(반투명 오버레이) + 바깥 영역 탭으로 닫기 지원
- 스크롤 가능한 콘텐츠와 시트 드래그 간 제스처 충돌 해결 필요 (스크롤 최상단에서만 시트 드래그)

### 2.6 스와이프 내비게이션 (Swipe Navigation / 스와이프 탭 전환)

| 항목 | 내용 |
|------|------|
| **설명** | 좌우 스와이프로 탭이나 페이지 간 이동하는 패턴. 상단 탭 인디케이터와 결합하여 현재 위치를 표시한다. |
| **UX 원칙** | **공간적 기억 (Spatial Memory)** — 콘텐츠를 공간적으로 배치하면 사용자가 위치를 기억하기 쉽다. **직접 조작** — 스와이프 거리에 비례한 페이지 이동으로 물리적 조작감 제공. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Medium |
| **실제 사례** | 카카오톡 채팅방 목록(좌측 스와이프→메뉴), Tinder 카드 스와이프, iOS 날씨 앱 도시 전환, Chrome 모바일 탭 전환 |

**구현 팁:**
- 스와이프 방향의 다음 페이지를 미리보기로 살짝 보여주어 "더 있음"을 암시
- 첫 페이지/마지막 페이지에서는 바운스 효과로 끝임을 전달
- ViewPager(Android) 또는 UIPageViewController(iOS)와 같은 플랫폼 네이티브 컴포넌트 활용
- 탭 인디케이터의 밑줄이 스와이프 제스처에 따라 함께 이동하는 연동 애니메이션 구현

## 3. 피드백 및 응답 (Feedback & Response)

시스템이 사용자의 행동에 적절히 반응하는 것은 신뢰 구축의 핵심이다. Nielsen의 휴리스틱 1번 "시스템 상태의 가시성(Visibility of System Status)"은 모든 피드백 패턴의 근간이 된다.

### 3.1 햅틱 피드백 (Haptic Feedback / 촉각 반응)

| 항목 | 내용 |
|------|------|
| **설명** | 터치 인터랙션에 진동 반응을 결합하여 물리적 조작감을 제공하는 패턴. iOS의 Taptic Engine, Android의 HapticFeedback API를 활용한다. |
| **UX 원칙** | **다중 감각 피드백 (Multisensory Feedback)** — 시각+촉각을 결합하면 단일 감각보다 인지 정확도가 높아진다. **어포던스 (Affordance)** — 물리 버튼처럼 "눌린 느낌"을 재현하여 행동 완료를 확인. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Low |
| **실제 사례** | iPhone 키보드 타이핑, Apple Watch Digital Crown, 토스 송금 완료 진동, 삼성 One UI 터치 피드백 |

**구현 팁:**
- iOS: `UIImpactFeedbackGenerator` (light/medium/heavy), `UINotificationFeedbackGenerator` (success/warning/error)
- Android: `HapticFeedbackConstants.LONG_PRESS`, `VIRTUAL_KEY` 등 시스템 상수 활용
- 웹: `navigator.vibrate()` API (Android Chrome 지원, iOS Safari 미지원)
- 과도한 햅틱은 배터리 소모 + 사용자 피로 유발 — 중요 액션에만 선별적 적용

### 3.2 스켈레톤 스크린 (Skeleton Screen / 뼈대 화면)

| 항목 | 내용 |
|------|------|
| **설명** | 데이터 로딩 중 실제 UI 레이아웃의 빈 뼈대를 회색 블록으로 먼저 보여주는 패턴. 스피너보다 체감 로딩 시간을 단축시킨다. |
| **UX 원칙** | **인지된 성능 (Perceived Performance)** — 실제 속도가 아닌 사용자가 "느끼는" 속도가 중요하다. 스켈레톤은 콘텐츠가 곧 나타날 것이라는 기대감을 형성한다. Luke Wroblewski의 연구에서 스켈레톤 스크린이 스피너보다 체감 대기 시간을 단축하는 것으로 확인되었다. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Facebook 피드, LinkedIn 프로필, YouTube 동영상 목록, 네이버 뉴스, 배달의민족 |

**구현 팁:**
- 실제 콘텐츠와 동일한 레이아웃으로 스켈레톤 구성 (높이, 너비, 간격 일치)
- 시머(shimmer) 애니메이션: `background: linear-gradient(90deg, #f0f0f0 25%, #e0e0e0 50%, #f0f0f0 75%)` + `animation: shimmer 1.5s infinite`
- 텍스트 영역은 여러 줄의 둥근 사각형, 이미지는 정사각/원형 블록으로 표현
- 데이터 도착 시 fade-in 트랜지션으로 자연스럽게 대체

### 3.3 낙관적 업데이트 (Optimistic Update / 선반영 업데이트)

| 항목 | 내용 |
|------|------|
| **설명** | 서버 응답을 기다리지 않고 UI를 먼저 업데이트한 뒤, 실패 시 롤백하는 패턴. 네트워크 지연을 사용자에게 감추어 즉각적인 반응감을 제공한다. |
| **UX 원칙** | **도허티 임계값 (Doherty Threshold)** — 400ms 이내 응답이 최적. 네트워크 왕복은 이를 초과하므로 UI 선반영으로 체감 속도 개선. **신뢰 설계 (Trust Design)** — 대부분의 요청이 성공한다면 성공을 기본 가정으로 삼아 UX 최적화. |
| **플랫폼** | Both |
| **구현 복잡도** | High |
| **실제 사례** | Instagram 좋아요, Twitter/X 트윗 게시, Slack 메시지 전송, iMessage 말풍선 |

**구현 팁:**
- 실패 시 롤백 로직 필수 — 이전 상태 스냅샷 보관
- 실패 시 토스트 알림으로 사용자에게 알리고 재시도 옵션 제공
- TanStack Query의 `useMutation` + `onMutate`(낙관적 업데이트) + `onError`(롤백) 패턴 활용
- 결제, 삭제 등 되돌리기 어려운 작업에는 낙관적 업데이트 적용 금지

### 3.4 프로그레스 인디케이터 (Progress Indicator / 진행 표시기)

| 항목 | 내용 |
|------|------|
| **설명** | 작업의 진행 정도를 시각적으로 보여주는 패턴. 결정형(determinate: 퍼센트 표시)과 비결정형(indeterminate: 무한 루프)으로 나뉜다. |
| **UX 원칙** | **목표 구배 효과 (Goal-Gradient Effect)** — 목표에 가까워질수록 행동이 빨라진다. 프로그레스 바는 "거의 다 됐다"는 느낌을 주어 이탈 방지. **엔도우드 프로그레스 효과 (Endowed Progress Effect)** — 0%에서 시작하는 것보다 이미 일부 진행된 것처럼 보여주면 완료 동기가 높아진다. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | YouTube 영상 업로드, GitHub Actions 빌드 진행, LinkedIn 프로필 완성도, 네이버 클라우드 파일 업로드 |

**구현 팁:**
- 전체 소요 시간을 예측할 수 있으면 결정형(퍼센트) 사용, 예측 불가하면 비결정형 사용
- 프로그레스 바는 끝에 가까워질수록 느려지는 것이 자연스러움 (실제와 일치)
- 단계별 작업은 스텝 인디케이터(Step 1/3, Step 2/3, Step 3/3)로 표현
- `<progress>` HTML 요소 사용 — 기본 접근성 지원

### 3.5 토스트/스낵바 알림 (Toast/Snackbar Notification / 일시 알림)

| 항목 | 내용 |
|------|------|
| **설명** | 화면 상단 또는 하단에 일시적으로 나타났다 사라지는 짧은 메시지. 사용자의 작업 흐름을 방해하지 않으면서 정보를 전달한다. |
| **UX 원칙** | **최소 방해 원칙 (Minimal Interruption)** — 사용자의 현재 작업을 중단시키지 않고 부가 정보 전달. **자동 해제 (Auto-dismiss)** — 사용자 액션 불필요, 시간 기반 자동 소멸로 인지 부담 최소화. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Gmail "메일이 전송되었습니다" + 실행취소, Android Material Snackbar, Slack 알림, VS Code 알림 |

**구현 팁:**
- 표시 시간: 짧은 메시지 3초, 긴 메시지 5초, 액션 포함 시 8초
- 되돌릴 수 있는 작업에는 "실행취소(Undo)" 액션 버튼 포함
- 동시에 여러 토스트가 쌓이면 큐(queue) 방식으로 순차 표시
- `role="status"` 또는 `aria-live="polite"`로 스크린 리더 접근성 확보
- 에러 토스트는 자동 소멸하지 않고 사용자가 직접 닫도록 설계

## 4. 제스처 기반 인터랙션 (Gesture-based Interactions)

터치 디바이스에서 제스처는 물리적 세계의 조작 경험을 디지털로 전이한 것이다. 잘 설계된 제스처는 직관적이고 효율적이지만, 발견 가능성(discoverability)이 낮다는 한계가 있으므로 항상 대안적 조작 수단을 병행해야 한다.

### 4.1 스와이프 액션 (Swipe Actions / 밀어서 동작)

| 항목 | 내용 |
|------|------|
| **설명** | 리스트 아이템을 좌우로 스와이프하면 삭제, 보관, 읽음 처리 등의 빠른 액션이 나타나는 패턴. |
| **UX 원칙** | **효율성 (Efficiency of Use)** — 숙련 사용자에게 단축 경로를 제공하여 작업 속도 향상. **점진적 공개 (Progressive Disclosure)** — 기본 화면은 깔끔하게 유지하면서 필요할 때만 액션을 노출. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Medium |
| **실제 사례** | iOS Mail (스와이프→삭제/보관/플래그), Gmail, Todoist (스와이프→완료/일정변경), 카카오톡 채팅방 |

**구현 팁:**
- 좌측 스와이프와 우측 스와이프에 서로 다른 액션 배치 (예: 좌→삭제, 우→보관)
- 스와이프 거리에 따라 액션 아이콘+색상 노출 → 임계값 초과 시 자동 실행
- 삭제 액션은 빨간색, 보관은 파란색/회색 등 의미적 색상 코드 준수
- 실수 방지를 위해 삭제 시 "실행취소" 토스트 제공 (되돌리기 가능 설계)

### 4.2 핀치 투 줌 (Pinch-to-Zoom / 확대/축소)

| 항목 | 내용 |
|------|------|
| **설명** | 두 손가락을 벌리거나 오므려 콘텐츠를 확대/축소하는 멀티터치 제스처. 2007년 iPhone 발표에서 대중화되었다. |
| **UX 원칙** | **직접 조작 (Direct Manipulation)** — 콘텐츠를 직접 잡아 늘리는 물리적 경험을 재현. **자연 매핑 (Natural Mapping)** — 손가락 사이 거리와 확대 비율의 직관적 대응. |
| **플랫폼** | Mobile (Web에서는 `Ctrl+스크롤` 또는 트랙패드 제스처) |
| **구현 복잡도** | Medium |
| **실제 사례** | Google Maps 지도 확대, 사진 앱 이미지 확대, Safari 웹페이지 확대, Figma 캔버스 줌 |

**구현 팁:**
- 최소/최대 줌 레벨 설정 (일반적으로 1x~5x)
- 줌 중심점은 두 손가락의 중간 지점으로 설정
- 더블탭으로 빠른 줌인/줌아웃 대안 제공 (접근성 및 한 손 조작)
- 웹에서 `touch-action: none`으로 브라우저 기본 줌 방지 후 커스텀 구현 (지도 등 특수 UI에서만)

### 4.3 드래그 앤 드롭 (Drag and Drop / 끌어서 놓기)

| 항목 | 내용 |
|------|------|
| **설명** | 요소를 잡아 원하는 위치로 이동시키는 인터랙션. 순서 변경, 분류, 레이아웃 배치 등에 사용된다. |
| **UX 원칙** | **직접 조작 + 공간적 기억** — 물리적 세계에서 물건을 옮기는 경험의 디지털 전이. 드래그 대상과 드롭 대상의 시각적 관계가 직관적이어야 한다. |
| **플랫폼** | Both (데스크톱 우선, 모바일에서는 long press + drag) |
| **구현 복잡도** | High |
| **실제 사례** | Trello 카드 이동, Notion 블록 재배치, Figma 레이어 순서 변경, 앱 아이콘 재배치(iOS/Android) |

**구현 팁:**
- 드래그 시작 시 원본에 반투명 복사본(ghost) 표시, 드롭 가능 영역 하이라이트
- 모바일에서는 long press(300~500ms)로 드래그 모드 진입, 시작 시 햅틱 피드백 제공
- 드롭 가능 영역에 가까워지면 스냅(snap) 효과로 정확한 배치 유도
- `aria-grabbed`, `aria-dropeffect` ARIA 속성으로 접근성 확보
- 라이브러리: `@dnd-kit/core` (React), `SortableJS`, `react-beautiful-dnd`

### 4.4 롱 프레스 (Long Press / 길게 누르기)

| 항목 | 내용 |
|------|------|
| **설명** | 요소를 길게 누르면 컨텍스트 메뉴, 미리보기, 편집 모드 등이 활성화되는 패턴. 데스크톱의 우클릭에 해당한다. |
| **UX 원칙** | **점진적 공개 (Progressive Disclosure)** — 자주 사용하지 않는 기능을 숨겨 인터페이스를 단순화하면서도 접근 가능하게 유지. **2차 액션 (Secondary Action)** — 탭(1차 액션)과 구분되는 2차 인터랙션 채널 제공. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Low |
| **실제 사례** | iOS 3D Touch/Haptic Touch 미리보기, WhatsApp 메시지 반응, 카카오톡 메시지 복사/삭제/답장, Android 앱 아이콘 숏컷 |

**구현 팁:**
- 롱 프레스 인식 시간: 300~500ms (너무 짧으면 의도치 않은 활성화, 너무 길면 답답함)
- 롱 프레스 시작 시 시각적 피드백(크기 증가, 하이라이트) + 햅틱 피드백 제공
- 롱 프레스로만 접근 가능한 필수 기능은 없어야 함 — 항상 대안 경로(메뉴 버튼 등) 제공
- iOS에서는 Context Menu API, Android에서는 `setOnLongClickListener` 활용

### 4.5 더블 탭 (Double Tap / 두 번 탭)

| 항목 | 내용 |
|------|------|
| **설명** | 동일 위치를 빠르게 두 번 탭하여 특정 액션(좋아요, 줌인, 선택 등)을 실행하는 패턴. |
| **UX 원칙** | **효율성 (Shortcut)** — 숙련 사용자에게 빠른 접근 경로 제공. 단, 발견 가능성이 낮으므로 유일한 접근 방법이 되어서는 안 된다. |
| **플랫폼** | Mobile |
| **구현 복잡도** | Low |
| **실제 사례** | Instagram 더블탭 좋아요, iOS 사진 앱 더블탭 줌, YouTube 더블탭 10초 이동, Android 화면 더블탭 깨우기 |

**구현 팁:**
- 더블 탭 인식 간격: 200~300ms
- 단일 탭과의 혼동 방지 — 단일 탭에 300ms 딜레이를 넣는 것은 UX 저하이므로, 더블 탭은 단일 탭과 다른 보조적 액션에만 할당
- 더블 탭 성공 시 명확한 시각 피드백 (예: Instagram의 큰 하트 오버레이)
- 접근성을 위해 동일 액션에 대한 버튼 대안 항상 제공

## 5. 스크롤 인터랙션 (Scroll Interactions)

스크롤은 웹과 모바일에서 가장 빈번한 인터랙션이다. 스크롤과 결합한 인터랙션은 콘텐츠 소비 경험을 풍부하게 만들지만, 성능 최적화가 핵심이다.

### 5.1 패럴랙스 스크롤링 (Parallax Scrolling / 시차 스크롤)

| 항목 | 내용 |
|------|------|
| **설명** | 배경과 전경이 서로 다른 속도로 스크롤되어 깊이감(depth)을 만드는 시각 효과. |
| **UX 원칙** | **깊이 인식 (Depth Perception)** — 운동 시차(motion parallax)는 인간의 깊이 인식 메커니즘을 활용한 자연스러운 시각 효과. **몰입감 (Immersion)** — 평면적 화면에 3차원적 경험을 부여하여 콘텐츠 몰입도 향상. |
| **플랫폼** | Web (모바일에서는 성능 이슈로 주의) |
| **구현 복잡도** | Medium |
| **실제 사례** | Apple 제품 페이지 (iPhone, MacBook), Nike 랜딩 페이지, Spotify Year Wrapped, 삼성 Galaxy 페이지 |

**구현 팁:**
- CSS `transform: translate3d()`로 GPU 가속 활용 (will-change: transform)
- 모바일에서는 패럴랙스 비활성화 또는 경량화 — 스크롤 성능이 최우선
- `prefers-reduced-motion` 미디어 쿼리로 모션 감소 설정 존중
- Intersection Observer API로 뷰포트 진입 시에만 애니메이션 실행 (성능 최적화)

### 5.2 무한 스크롤 (Infinite Scroll / 무한 스크롤)

| 항목 | 내용 |
|------|------|
| **설명** | 페이지 하단에 도달하면 자동으로 다음 콘텐츠를 로딩하여 끊김 없는 탐색 경험을 제공하는 패턴. |
| **UX 원칙** | **흐름 상태 (Flow State)** — Mihaly Csikszentmihalyi의 Flow 이론. 중단 없는 콘텐츠 스트림이 몰입 상태를 유지시킨다. 다만, 푸터 접근 불가, 위치 상실, "끝"이 없는 불안감 등의 부작용이 있다. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Instagram 피드, Twitter/X 타임라인, Pinterest 핀 보드, Facebook 뉴스피드 |

**구현 팁:**
- Intersection Observer로 "센티넬 요소"가 뷰포트 진입 시 다음 페이지 로딩
- "맨 위로" 버튼(FAB) 항상 제공 — 긴 스크롤 후 복귀 수단
- 더 이상 콘텐츠가 없으면 "모든 콘텐츠를 확인했습니다" 메시지 표시
- 뒤로가기 후 복귀 시 이전 스크롤 위치 복원 필수
- 탐색적 콘텐츠(피드)에는 무한 스크롤, 목적 지향 콘텐츠(검색 결과)에는 페이지네이션이 적합

### 5.3 고정 헤더 (Sticky Header / 고정 머리글)

| 항목 | 내용 |
|------|------|
| **설명** | 스크롤 시 헤더(내비게이션 바)가 화면 상단에 고정되어 항상 접근 가능한 패턴. 스크롤 방향에 따라 숨김/표시되는 변형도 있다. |
| **UX 원칙** | **접근성 유지 (Persistent Accessibility)** — 핵심 내비게이션을 항상 사용 가능하게 유지. **피츠의 법칙** — 화면 가장자리에 고정하면 무한한 타겟 크기 효과(화면 경계가 자연스러운 정지점). |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | 네이버 상단바, Amazon 검색바, Medium 읽기 진행 표시, GitHub 파일 브라우저 헤더 |

**구현 팁:**
- CSS `position: sticky; top: 0;` 로 간단 구현
- 아래로 스크롤 시 헤더 숨김, 위로 스크롤 시 헤더 표시 (show-on-scroll-up) — `scroll` 이벤트로 방향 감지
- 헤더 높이만큼 콘텐츠에 padding-top 적용하여 겹침 방지
- 모바일에서는 화면 크기가 작으므로 스크롤 시 컴팩트 헤더로 축소하여 콘텐츠 영역 확보

### 5.4 스크롤 트리거 애니메이션 (Scroll-triggered Animation / 스크롤 연동 애니메이션)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자가 스크롤하여 특정 요소가 뷰포트에 진입할 때 애니메이션(fade-in, slide-up 등)이 실행되는 패턴. |
| **UX 원칙** | **주의 유도 (Attention Direction)** — 움직임은 인간의 시각적 주의를 자동으로 끌어당긴다. 중요한 콘텐츠에 선별적으로 적용하면 정보 계층 구조를 강화한다. **점진적 공개** — 모든 정보를 한꺼번에 보여주지 않고 스크롤에 따라 순차적으로 공개. |
| **플랫폼** | Web (모바일 앱에서는 성능 고려 필요) |
| **구현 복잡도** | Medium |
| **실제 사례** | Apple 제품 페이지, Stripe 홈페이지, 토스 서비스 소개 페이지, Airbnb 호스트 소개 |

**구현 팁:**
- Intersection Observer API (threshold: 0.1~0.3)로 뷰포트 진입 감지
- CSS `@keyframes` + `animation-fill-mode: forwards`로 최종 상태 유지
- 라이브러리: AOS (Animate On Scroll), Framer Motion, GSAP ScrollTrigger
- 애니메이션은 한 번만 실행 (매번 실행하면 산만함)
- `prefers-reduced-motion` 대응 필수 — 모션 감소 시 즉시 표시

### 5.5 스크롤 스냅 (Scroll Snap / 스크롤 정렬)

| 항목 | 내용 |
|------|------|
| **설명** | 스크롤이 끝날 때 가장 가까운 콘텐츠 경계에 자동으로 정렬(snap)되는 패턴. 카드 캐러셀, 전체 화면 섹션 등에 활용. |
| **UX 원칙** | **정렬 원칙 (Alignment)** — 콘텐츠가 중간에 걸리지 않고 깔끔하게 정렬되어 시각적 완성도 향상. **예측 가능성 (Predictability)** — 스크롤 결과가 예측 가능하여 사용자 통제감 유지. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Instagram 릴스 (세로 스냅), TikTok 피드, App Store 앱 카드 캐러셀, 당근마켓 이미지 캐러셀 |

**구현 팁:**
- CSS `scroll-snap-type: x mandatory` (가로) 또는 `y mandatory` (세로)
- 자식 요소에 `scroll-snap-align: start | center | end` 적용
- `mandatory`는 항상 스냅, `proximity`는 스냅 포인트 근처에서만 스냅
- 페이지네이션 닷(dots)으로 현재 위치와 전체 개수 표시

## 6. 폼 인터랙션 (Form Interactions)

폼은 사용자와 시스템 간 데이터 교환의 핵심 인터페이스이다. 잘 설계된 폼은 완료율을 극적으로 향상시킨다. Luke Wroblewski의 연구에 따르면 폼 최적화만으로 전환율이 25~40% 개선될 수 있다.

### 6.1 인라인 유효성 검사 (Inline Validation / 즉시 검증)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자가 입력 필드를 벗어나거나(blur) 입력하는 동안 실시간으로 유효성을 검사하여 피드백을 제공하는 패턴. |
| **UX 원칙** | **즉각적 피드백 (Immediate Feedback)** — 오류를 즉시 발견하면 수정 비용이 낮아진다. 제출 후 전체 에러 목록을 보여주는 것보다 필드별 즉시 피드백이 효과적이다. Luke Wroblewski의 연구에서 인라인 검증이 제출 후 검증보다 완료 시간 22% 단축, 에러 발생 22% 감소를 확인. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Gmail 가입 (이메일 중복 체크), GitHub 저장소 이름 검증, 토스 계좌번호 입력, 네이버 회원가입 |

**구현 팁:**
- **시점이 중요**: 입력 중(onChange)이 아닌 포커스 이탈 시(onBlur)에 검증 — 입력 중 에러 메시지는 방해
- 단, 비밀번호 강도 같은 "긍정적 피드백"은 입력 중 실시간 표시 가능
- 에러 메시지는 필드 바로 아래에 빨간색으로 표시, 아이콘(✗) 병행
- 성공 상태도 표시 — 녹색 체크마크(✓)로 "이 필드는 OK"를 확인
- `aria-describedby`로 에러 메시지를 필드에 연결 (접근성)

### 6.2 플로팅 라벨 (Floating Labels / 떠다니는 라벨)

| 항목 | 내용 |
|------|------|
| **설명** | 입력 필드의 placeholder가 사용자가 입력을 시작하면 필드 위로 올라가 라벨로 변환되는 패턴. Material Design에서 대중화. |
| **UX 원칙** | **공간 효율성 (Space Efficiency)** — 라벨과 placeholder를 하나로 합쳐 수직 공간 절약. **맥락 유지 (Context Retention)** — placeholder만 사용하면 입력 후 어떤 필드인지 알 수 없는 문제를 해결. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Material Design 전 제품군, Airbnb 검색 폼, 토스 송금 입력, Stripe 결제 폼 |

**구현 팁:**
- 라벨 전환 애니메이션: `transform: translateY(-20px) scale(0.75)` + `transition: 200ms`
- `<label>` 요소를 반드시 사용하고 `for` 속성으로 input에 연결 (접근성)
- 입력값이 있는 상태에서 라벨은 항상 올라간 위치 유지
- 라벨 크기가 줄어들 때 가독성 저하 — 최소 12px 이상 유지
- 에러 상태에서는 라벨 + 테두리 색상을 빨간색으로 변경

### 6.3 자동완성 (Auto-complete / 자동 완성)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자 입력에 따라 가능한 선택지를 실시간으로 제시하여 빠른 입력을 돕는 패턴. |
| **UX 원칙** | **힉의 법칙 (Hick's Law)** — 선택지가 많을수록 결정 시간이 늘어난다. 자동완성은 관련 없는 선택지를 필터링하여 결정 시간 단축. **인식 vs 기억 (Recognition over Recall)** — 사용자가 기억해내는 것보다 목록에서 인식하는 것이 쉽다 (Nielsen 휴리스틱 6번). |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Google 검색 자동완성, GitHub 이슈/멘션(@), Slack 채널/멘션, 네이버 지도 주소 검색, 카카오 주소 API |

**구현 팁:**
- 최소 2~3글자 입력 후 제안 시작 (1글자는 너무 많은 결과)
- 디바운스(debounce) 200~300ms 적용하여 서버 요청 최적화
- 키보드 탐색(↑↓) + Enter 선택 지원
- 검색어 매칭 부분 하이라이트(bold) 처리
- `role="combobox"`, `aria-autocomplete`, `aria-activedescendant` ARIA 패턴 적용
- 최근 검색어 / 인기 검색어를 입력 전 빈 상태에서 표시

### 6.4 스마트 기본값 (Smart Defaults / 지능형 기본값)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자의 맥락(위치, 시간, 이전 입력, 통계적 다수)을 기반으로 가장 가능성 높은 값을 미리 채워주는 패턴. |
| **UX 원칙** | **최소 노력 원칙 (Principle of Least Effort)** — 사용자는 목표 달성을 위해 최소한의 에너지를 사용하려 한다. **기본값 효과 (Default Effect)** — 사전에 설정된 기본값을 변경하지 않는 경향이 압도적 (옵트아웃 방식 대비 옵트인은 참여율이 50~90% 낮음). |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | 항공권 예매 사이트의 출발지(현재 위치 기반), 배달앱의 기본 배송지, 캘린더의 기본 1시간 일정, EC 사이트의 이전 배송지 자동 채움 |

**구현 팁:**
- GPS 기반 국가/도시 자동 선택, 브라우저 언어 기반 언어 설정
- 이전 입력 패턴 학습: 최근 사용한 주소, 결제 수단 등 우선 표시
- 통계적으로 가장 흔한 값을 기본값으로 (예: 국가 선택에서 서비스 주요 시장을 최상단에)
- 기본값은 언제든 변경 가능해야 하며, 변경이 쉬워야 함

### 6.5 단계별 마법사 (Step-by-Step Wizard / 단계별 입력)

| 항목 | 내용 |
|------|------|
| **설명** | 복잡한 폼을 여러 단계로 나누어 한 번에 하나씩 처리하는 패턴. 각 단계에 프로그레스 인디케이터를 표시한다. |
| **UX 원칙** | **청킹 (Chunking)** — George Miller의 이론. 정보를 작은 덩어리로 나누면 인지 부하가 감소한다. **목표 구배 효과 (Goal-Gradient Effect)** — 진행 표시가 완료 동기를 높인다. **완료 편향 (Completion Bias)** — 시작한 프로세스를 끝내려는 심리적 경향. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | TurboTax 세금 신고, Typeform 설문, 토스 계좌 개설, 배달의민족 가게 등록, Airbnb 숙소 등록 |

**구현 팁:**
- 단계 수를 미리 표시하여 전체 분량 예측 가능하게 (Step 2 of 4)
- 이전 단계로 돌아갈 수 있어야 함 (입력값 보존)
- 각 단계는 3~5개 필드 이하로 제한
- 마지막 단계에서 전체 입력 요약(review) 화면 제공
- 부분 저장(draft) 기능으로 중간 이탈 후 복귀 가능하게

### 6.6 입력 마스크 (Input Mask / 입력 형식 안내)

| 항목 | 내용 |
|------|------|
| **설명** | 전화번호(010-1234-5678), 카드번호(1234 5678 9012 3456) 등 특정 형식의 입력을 자동으로 포맷팅하는 패턴. |
| **UX 원칙** | **오류 예방 (Error Prevention)** — Nielsen 휴리스틱 5번. 오류 메시지보다 애초에 오류가 발생하지 않도록 설계하는 것이 우월하다. **인지 부하 감소** — 형식을 사용자가 기억할 필요 없이 시스템이 자동 적용. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Stripe 카드 결제 (카드번호 4자리 분리), 토스 계좌번호 입력, 네이버 휴대폰 인증 |

**구현 팁:**
- 숫자만 필요한 필드에는 `inputmode="numeric"` (모바일 숫자 키패드 표시)
- 자동 하이픈/공백 삽입은 입력 방향(추가/삭제)을 고려하여 구현
- 마스크 적용 시 커서 위치가 올바르게 유지되도록 주의 (cursor jump 방지)
- 라이브러리: `cleave.js`, `react-input-mask`, `imask`
- 서버 전송 시에는 포맷 문자를 제거한 순수 값 전송

## 7. 전환 및 애니메이션 (Transition & Animation)

애니메이션은 사용자의 인지 모델을 돕는 도구이다. 어디서 왔고 어디로 가는지, 무엇이 변했는지를 설명하는 시각적 내러티브를 제공한다. 12가지 디즈니 애니메이션 원칙(1981)은 디지털 UI 애니메이션에도 유효하다.

### 7.1 페이지 전환 (Page Transition / 화면 전환)

| 항목 | 내용 |
|------|------|
| **설명** | 페이지 간 이동 시 슬라이드, 페이드, 줌 등의 애니메이션으로 공간적 연속성을 제공하는 패턴. |
| **UX 원칙** | **공간적 일관성 (Spatial Consistency)** — 페이지 간 공간적 관계를 애니메이션으로 전달하면 사용자가 정보 구조를 직관적으로 이해한다. **연속성 원칙 (Continuity)** — 갑작스러운 전환(하드 컷)보다 부드러운 전환이 맥락 유지에 도움. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | iOS UINavigationController (push/pop slide), Material Design 컨테이너 전환, Next.js page transitions, 토스 화면 전환 |

**구현 팁:**
- 계층 이동(drill-down): 좌→우 슬라이드 진입, 우→좌 슬라이드 복귀
- 동일 계층(sibling): 페이드 또는 크로스 디졸브
- 전환 시간: 200~300ms (모바일), 150~250ms (데스크톱)
- Web: View Transitions API (`document.startViewTransition()`) 활용
- 전환 중 사용자 입력 차단으로 이중 내비게이션 방지

### 7.2 공유 요소 전환 (Shared Element Transition / 연결 전환)

| 항목 | 내용 |
|------|------|
| **설명** | 두 화면 간 공통 요소(이미지, 카드 등)가 위치와 크기를 애니메이션하며 자연스럽게 연결되는 패턴. |
| **UX 원칙** | **객체 항상성 (Object Constancy)** — 동일 객체가 변형되는 것으로 인식되어 "새 페이지가 열린 것"이 아닌 "기존 요소가 확장된 것"으로 느낀다. 이는 맥락 전환 비용을 대폭 줄인다. |
| **플랫폼** | Both |
| **구현 복잡도** | High |
| **실제 사례** | Google Photos 갤러리→상세, Material Design 카드 확장, iOS App Store 카드→상세, Airbnb 숙소 카드→상세 |

**구현 팁:**
- 두 화면에서 공유 요소에 동일 ID/태그 부여
- 시작/끝 위치·크기를 계산하여 `transform` 애니메이션 적용 (layout trigger 방지)
- FLIP 기법 (First, Last, Invert, Play): 최종 위치를 먼저 렌더링 → 역변환 → 애니메이션
- React: Framer Motion의 `layoutId`, Flutter: `Hero` widget, Android: `SharedElementTransition`
- Web: View Transitions API의 `view-transition-name` CSS 속성

### 7.3 모핑 애니메이션 (Morphing Animation / 형태 변환)

| 항목 | 내용 |
|------|------|
| **설명** | 한 형태가 다른 형태로 부드럽게 변화하는 애니메이션. 아이콘 변환(햄버거→X, 재생→일시정지), 버튼 형태 변경 등. |
| **UX 원칙** | **연속성과 변환 (Continuity & Transformation)** — 상태 변화를 시각적으로 연결하여 "무엇이 변했는지"를 즉각 이해하게 한다. 디즈니 애니메이션 원칙 중 "Squash and Stretch"의 디지털 적용. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Material Design 햄버거→화살표 아이콘, iOS 잠금 해제 아이콘 모핑, 음악 앱 재생/일시정지 버튼, Notion 토글 화살표 회전 |

**구현 팁:**
- SVG path 모핑: 두 SVG path의 포인트 수를 동일하게 맞추어 `d` 속성 보간
- CSS: `clip-path` 전환으로 간단한 형태 모핑 구현
- Lottie 파일로 복잡한 모핑 애니메이션을 디자이너가 제작, 개발자는 재생만
- 라이브러리: `flubber` (SVG morph), `anime.js`, Lottie

### 7.4 스프링 물리학 (Spring Physics / 스프링 동역학)

| 항목 | 내용 |
|------|------|
| **설명** | 기계적 이징(ease-in/out) 대신 스프링(질량, 강성, 감쇠) 기반 물리 시뮬레이션으로 자연스러운 움직임을 구현하는 패턴. |
| **UX 원칙** | **자연주의 (Naturalism)** — 실제 물리 법칙을 따르는 움직임은 인공적인 이징보다 자연스럽게 인식된다. 스프링은 목표를 초과했다 되돌아오는(overshoot) 특성이 있어 "살아있는" 느낌을 준다. **디즈니 원칙: Follow Through** — 주요 움직임이 멈춘 후에도 부차적 요소가 관성에 의해 추가로 움직이는 효과. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | iOS 전반의 UIKit Dynamics, Facebook/Meta 앱 전환, Framer Motion 기본 애니메이션, Apple 위젯 스택 |

**구현 팁:**
- 핵심 파라미터: `stiffness` (강성, 높을수록 빠름), `damping` (감쇠, 낮을수록 바운스 많음), `mass` (질량, 높을수록 무거운 느낌)
- React: `framer-motion`의 `type: "spring"`, React Native: `react-native-reanimated`의 `withSpring`
- CSS에서는 `cubic-bezier()`로 스프링 근사치 구현 가능하지만 한계 있음
- 대화형 요소(드래그 등)에 스프링을 적용하면 "손에서 놓았을 때" 자연스러운 복귀 효과

### 7.5 시차 애니메이션 (Staggered Animation / 순차 등장)

| 항목 | 내용 |
|------|------|
| **설명** | 여러 요소가 동시에 나타나지 않고 일정 간격(50~100ms)을 두고 순차적으로 등장하는 패턴. |
| **UX 원칙** | **시각적 계층 (Visual Hierarchy)** — 순차 등장은 자연스러운 읽기 순서를 안내한다. **주의 유도 (Attention Guidance)** — 한꺼번에 모든 요소가 나타나면 어디를 봐야 할지 모르지만, 순차 등장은 시선의 흐름을 만든다. **디즈니 원칙: Staging** — 관객의 시선을 의도한 곳으로 유도. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Material Design 리스트 아이템 등장, iOS 설정 목록 애니메이션, Notion 사이드바 확장, Slack 채널 목록 로딩 |

**구현 팁:**
- 각 요소에 `animation-delay: calc(index * 50ms)` 적용
- React: `framer-motion`의 `staggerChildren` 속성
- 처음 5~10개 요소에만 시차 적용 (그 이상은 기다림이 됨)
- 기본 애니메이션: `opacity: 0→1` + `translateY: 20px→0` 조합이 가장 보편적
- 같은 그룹 요소는 동일 방향에서 등장해야 일관성 유지

## 8. 온보딩 (Onboarding)

온보딩은 사용자가 제품의 가치를 최대한 빠르게 발견하도록 돕는 과정이다. 좋은 온보딩은 "가르치는 것"이 아니라 "경험하게 하는 것"이다. Samuel Hulick의 "더 나은 나를 위한 여정(Superhero Journey)" 프레임워크가 핵심 철학이다.

### 8.1 점진적 공개 (Progressive Disclosure / 단계적 노출)

| 항목 | 내용 |
|------|------|
| **설명** | 인터페이스의 기능을 한꺼번에 보여주지 않고 사용자의 진행도에 따라 단계적으로 노출하는 패턴. |
| **UX 원칙** | **힉의 법칙 (Hick's Law)** — 선택지가 적을수록 결정이 빠르다. 처음에는 핵심 기능만 노출하고 숙련도에 따라 고급 기능을 공개. **인지 부하 감소** — 한 번에 처리해야 할 정보량을 줄여 학습 부담 경감. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Notion (초기에 기본 블록만 표시, 점차 고급 블록 소개), Figma (기본 도구→고급 도구 순차 노출), Slack (채널 참여→앱 설치→워크플로 순차 안내) |

**구현 팁:**
- "더 보기" / "고급 옵션" 버튼으로 추가 기능 숨김
- 사용자 행동 기반 트리거: 특정 기능을 N회 사용 후 관련 고급 기능 소개
- 첫 사용 시 3~5개 이하의 핵심 액션에 집중
- 사용 빈도 분석으로 노출 순서 최적화 (자주 사용되는 기능이 먼저)

### 8.2 툴팁 (Tooltips / 도움말 말풍선)

| 항목 | 내용 |
|------|------|
| **설명** | UI 요소에 마우스를 올리거나 터치하면 해당 요소의 기능을 설명하는 작은 팝업이 표시되는 패턴. |
| **UX 원칙** | **인식 vs 기억 (Recognition over Recall)** — 기억하지 않아도 필요할 때 도움을 받을 수 있다. **맥락적 도움 (Contextual Help)** — 도움말 페이지로 이동하지 않고 현재 맥락에서 바로 학습. |
| **플랫폼** | Both (모바일에서는 hover 불가하므로 탭 또는 인포 아이콘 활용) |
| **구현 복잡도** | Low |
| **실제 사례** | GitHub 아이콘 툴팁, Figma 도구 설명, Jira 필드 도움말, Notion 단축키 안내 |

**구현 팁:**
- 툴팁 표시까지 200~500ms 딜레이 (의도하지 않은 hover에 반응 방지)
- 300ms warm-up, 즉각 사라짐 또는 100ms 지연 후 사라짐
- 최대 2줄 이내의 짧은 텍스트, 상세 설명이 필요하면 "자세히 보기" 링크 추가
- `role="tooltip"` + `aria-describedby`로 접근성 확보
- 모바일에서는 `(i)` 아이콘 탭 시 표시, 바깥 영역 탭 시 닫기

### 8.3 코치 마크 (Coach Marks / 기능 안내 오버레이)

| 항목 | 내용 |
|------|------|
| **설명** | 앱 처음 실행 시 주요 UI 요소를 하이라이트하고 순차적으로 설명하는 오버레이 안내 패턴. |
| **UX 원칙** | **안내된 탐색 (Guided Exploration)** — 자유 탐색보다 구조화된 안내가 초기 학습에 효과적. 다만, 과도한 코치 마크는 "설명이 필요한 복잡한 UI"를 의미할 수 있으므로 주의. |
| **플랫폼** | Both (모바일 앱에서 더 일반적) |
| **구현 복잡도** | Medium |
| **실제 사례** | Slack 신규 사용자 안내, Duolingo 첫 레슨 안내, 카카오톡 새 기능 소개, Instagram 릴스 첫 사용 |

**구현 팁:**
- 최대 3~5단계로 제한 (이보다 길면 사용자가 "건너뛰기"를 찾기 시작)
- "건너뛰기" 버튼 항상 제공
- 배경을 반투명 오버레이로 어둡게 하고 설명 대상만 밝게 강조 (spotlight effect)
- 사용자가 실제로 액션을 수행하게 하는 인터랙티브 방식이 수동적 읽기보다 학습 효과 높음
- 코치 마크 완료 상태를 로컬 저장소에 저장하여 재표시 방지

### 8.4 빈 상태 (Empty States / 빈 화면 디자인)

| 항목 | 내용 |
|------|------|
| **설명** | 콘텐츠가 없는 초기 상태에서 단순히 빈 화면을 보여주는 대신, 안내 메시지, 일러스트레이션, CTA(행동 유도) 버튼을 제공하는 패턴. |
| **UX 원칙** | **행동 유도 (Call to Action)** — 빈 상태는 사용자에게 "다음 행동"을 명확히 안내하는 기회. **첫인상 효과 (Primacy Effect)** — 첫 경험이 제품에 대한 전반적 인상을 결정한다. 빈 화면에 매력적 디자인을 적용하면 긍정적 첫인상 형성. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Dropbox "파일을 드래그하세요", Trello "첫 카드를 만들어보세요", Mailchimp 캠페인 빈 상태, 토스 증권 "관심 종목을 추가해보세요" |

**구현 팁:**
- 3가지 요소 포함: 일러스트(감성적 연결) + 설명 메시지(현재 상태 설명) + CTA 버튼(다음 행동)
- 빈 상태 유형별 대응: 첫 사용(온보딩 안내), 검색 결과 없음(검색어 수정 제안), 에러(재시도 안내), 완료(축하 메시지)
- 검색 빈 상태: "결과가 없습니다" 대신 "다른 키워드로 검색해보세요" + 인기 검색어 추천
- 일러스트는 브랜드 톤에 맞는 가볍고 친근한 스타일 (무거운 빈 상태는 부담)

### 8.5 기능 발견 (Feature Discovery / 새 기능 알림)

| 항목 | 내용 |
|------|------|
| **설명** | 새로운 기능이나 업데이트된 기능을 사용자에게 알리는 패턴. 뱃지, 펄스 애니메이션, "What's New" 모달 등. |
| **UX 원칙** | **자이가르닉 효과 (Zeigarnik Effect)** — 미완료된 것(미확인 뱃지)이 완료된 것보다 기억에 더 오래 남는다. 빨간 뱃지 점은 "확인하지 않은 것이 있다"는 긴장감을 유발하여 탐색을 촉진. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | iOS 앱 아이콘 뱃지, Slack "새로운 기능" 배너, Figma "What's new" 모달, 카카오톡 새 이모티콘 알림 |

**구현 팁:**
- 강도 계층: 뱃지 점(낮음) < 인라인 배너(중간) < 모달(높음) — 기능 중요도에 맞게 선택
- 최초 1회만 표시 + "다시 보지 않기" 옵션 제공
- 뱃지 점은 해당 기능 진입 시 자동 제거
- 과도한 알림은 "알림 피로(Notification Fatigue)"를 유발하므로 신중하게 사용
- 변경 로그(Changelog) 페이지를 별도로 운영하여 관심 있는 사용자가 자발적으로 탐색 가능하게

## 9. 접근성 인터랙션 (Accessibility Interactions)

접근성은 선택이 아닌 필수이다. WCAG 2.1 AA 기준은 법적 요구사항인 경우가 많으며(한국 장애인차별금지법, 미국 ADA 등), 접근성 향상은 모든 사용자의 경험을 개선한다 (커브 컷 효과, Curb Cut Effect).

### 9.1 스크린 리더 패턴 (Screen Reader Patterns / 화면 읽기 패턴)

| 항목 | 내용 |
|------|------|
| **설명** | 시각 장애 사용자가 스크린 리더(VoiceOver, TalkBack, NVDA)로 인터페이스를 탐색할 수 있도록 적절한 시맨틱 마크업과 ARIA 속성을 제공하는 패턴. |
| **UX 원칙** | **동등한 접근 (Equivalent Access)** — 모든 사용자가 동일한 정보와 기능에 접근할 수 있어야 한다 (WCAG 원칙 1: Perceivable). |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | gov.uk (영국 정부 웹사이트), Apple 제품 전반, 정부24 (대한민국), 네이버 접근성 강화 |

**구현 팁:**
- 시맨틱 HTML 우선: `<button>`, `<nav>`, `<main>`, `<article>`, `<header>`, `<footer>`
- 이미지에 의미 있는 `alt` 텍스트, 장식용 이미지에는 `alt=""` + `aria-hidden="true"`
- 동적 콘텐츠 변경 시 `aria-live="polite"` (비긴급) 또는 `aria-live="assertive"` (긴급)
- 커스텀 컴포넌트에 적절한 ARIA role: `role="dialog"`, `role="tablist"`, `role="alert"` 등
- 아이콘 버튼에 `aria-label` 필수 (예: `<button aria-label="닫기"><XIcon /></button>`)

### 9.2 포커스 관리 (Focus Management / 초점 관리)

| 항목 | 내용 |
|------|------|
| **설명** | 키보드 내비게이션 시 포커스가 논리적 순서로 이동하고, 모달/다이얼로그 열림 시 포커스가 적절히 이동·가둠(trap)되는 패턴. |
| **UX 원칙** | **키보드 접근성 (Keyboard Accessibility)** — 모든 인터랙티브 요소는 키보드만으로 접근·조작할 수 있어야 한다 (WCAG 2.1.1). **포커스 트래핑 (Focus Trapping)** — 모달 내에서 Tab 키가 모달 밖으로 나가지 않도록 가두어 맥락 혼란 방지. |
| **플랫폼** | Both (특히 Web) |
| **구현 복잡도** | Medium |
| **실제 사례** | Gmail 키보드 단축키, GitHub 이슈/PR 키보드 탐색, VS Code 전체, Jira 보드 |

**구현 팁:**
- `tabindex="0"` (자연 순서에 추가), `tabindex="-1"` (프로그래밍 포커스만), `tabindex` 양수값은 사용 금지
- 모달 열림: 포커스를 모달 첫 번째 인터랙티브 요소로 이동, Tab은 모달 내에서만 순환
- 모달 닫힘: 포커스를 모달을 연 트리거 요소로 복원
- `:focus-visible` (키보드 포커스일 때만 표시) vs `:focus` (모든 포커스에 표시) 구분
- `focus-trap` 라이브러리 또는 `<dialog>` 네이티브 요소의 기본 트래핑 활용

### 9.3 모션 감소 (Reduced Motion / 동작 줄이기)

| 항목 | 내용 |
|------|------|
| **설명** | 전정 기능 장애, 편두통, 주의력 장애 등을 가진 사용자를 위해 불필요한 애니메이션을 줄이거나 제거하는 패턴. |
| **UX 원칙** | **포용적 디자인 (Inclusive Design)** — 다양한 신체적·인지적 조건을 가진 사용자를 포용. 과도한 모션은 메스꺼움(vestibular disorder)이나 발작(photosensitive epilepsy)을 유발할 수 있다. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | iOS 설정 "동작 줄이기", macOS/Windows 접근성 설정, Apple.com (패럴랙스 대체), Stripe 홈페이지 |

**구현 팁:**
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```
- 모션을 완전히 제거하지 말고 크로스페이드(fade)로 대체 — 맥락 전환의 이해를 돕는 최소한의 전환은 유지
- 자동 재생되는 비디오/GIF에 정지 버튼 제공
- 패럴랙스, 시차 애니메이션, 자동 캐러셀은 `prefers-reduced-motion: reduce` 시 비활성화

### 9.4 색상 대비 (Color Contrast / 색상 명도 대비)

| 항목 | 내용 |
|------|------|
| **설명** | 텍스트와 배경 간 충분한 명도 대비를 확보하여 저시력·색각 이상 사용자도 콘텐츠를 읽을 수 있도록 하는 패턴. |
| **UX 원칙** | **인식 가능성 (Perceivability)** — WCAG 원칙 1. 정보는 사용자가 인식할 수 있는 방식으로 제시되어야 한다. WCAG 1.4.3: 일반 텍스트 4.5:1, 큰 텍스트 3:1 최소 대비비. |
| **플랫폼** | Both |
| **구현 복잡도** | Low |
| **실제 사례** | Material Design 색상 시스템, Apple HIG 색상 가이드, 정부24 고대비 모드, 네이버 접근성 |

**구현 팁:**
- WCAG AA 최소 기준: 일반 텍스트(14px 이하) 4.5:1, 큰 텍스트(18px 이상 또는 14px bold) 3:1
- WCAG AAA 권장 기준: 일반 텍스트 7:1, 큰 텍스트 4.5:1
- 색상만으로 정보를 전달하지 말 것 — 아이콘, 패턴, 텍스트 라벨 병행 (색맹 대응)
- 도구: WebAIM Contrast Checker, Chrome DevTools Contrast 검사, Figma A11y 플러그인
- 고대비 모드(High Contrast Mode) 대응: `@media (forced-colors: active)` + 시스템 색상 키워드

### 9.5 터치 타겟 크기 (Touch Target Sizing / 터치 영역 크기)

| 항목 | 내용 |
|------|------|
| **설명** | 인터랙티브 요소의 터치/클릭 가능 영역을 충분히 크게 설정하여 운동 장애, 손가락이 큰 사용자도 정확히 조작할 수 있게 하는 패턴. |
| **UX 원칙** | **피츠의 법칙 (Fitts's Law)** — 타겟이 클수록, 가까울수록 빠르고 정확하게 접근할 수 있다. 작은 타겟은 오류를 유발하고 사용자를 좌절시킨다. |
| **플랫폼** | Both (특히 Mobile) |
| **구현 복잡도** | Low |
| **실제 사례** | iOS Human Interface Guidelines (44x44pt), Material Design (48x48dp), WCAG 2.5.8 (24x24 CSS px), 정부24 |

**구현 팁:**
- 최소 터치 타겟: 44x44pt (iOS) / 48x48dp (Android) / 24x24px (WCAG AA, 44x44px AAA 권장)
- 시각적 크기가 작아도 터치 영역은 크게: `padding`으로 터치 영역 확장
- 인접한 터치 타겟 간 최소 8dp 간격 유지 (실수 방지)
- 링크 텍스트가 짧은 경우(예: "here") 패딩을 추가하여 터치 영역 확보
- `min-height: 44px; min-width: 44px;` CSS 규칙을 인터랙티브 요소 기본 스타일에 포함

## 10. 딜라이트 패턴 (Delight Patterns)

딜라이트는 기능적 요구사항을 넘어 감성적 만족을 제공하는 디자인 요소이다. Don Norman의 "감성 디자인(Emotional Design)" 3단계 중 "반사적(Reflective)" 수준에 해당하며, 브랜드 차별화와 사용자 충성도에 기여한다. 단, 기본적인 사용성(Usability)이 확보된 후에 적용해야 한다 — 불편한 제품에 딜라이트를 더하면 오히려 역효과.

### 10.1 이스터 에그 (Easter Eggs / 숨겨진 재미)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자가 우연히 또는 의도적으로 발견하는 숨겨진 기능이나 메시지. 브랜드 개성을 전달하고 입소문을 유발한다. |
| **UX 원칙** | **가변 보상 (Variable Reward)** — Nir Eyal의 Hook Model. 예측할 수 없는 보상이 탐색 동기를 높인다. **발견의 기쁨 (Joy of Discovery)** — 스스로 찾아낸 것에 대한 성취감과 소속감. |
| **플랫폼** | Both |
| **구현 복잡도** | Low~Medium |
| **실제 사례** | Google 검색 "do a barrel roll", Chrome 공룡 게임(오프라인), Slack 로딩 메시지, GitHub 404 페이지 Parallax, VS Code Konami Code |

**구현 팁:**
- 핵심 기능에 영향을 주지 않는 곳에 배치 (404 페이지, 로딩 화면, 설정 심층부 등)
- 발견하지 못해도 제품 사용에 지장 없도록 설계
- 팀 문화나 브랜드 성격에 맞는 유머 수준 유지
- Konami Code (↑↑↓↓←→←→BA) 같은 클래식한 트리거 활용

### 10.2 축하 애니메이션 (Celebration Animation / 성취 축하 효과)

| 항목 | 내용 |
|------|------|
| **설명** | 목표 달성, 과제 완료, 마일스톤 도달 시 컨페티(색종이), 불꽃놀이, 배지 획득 등의 시각적 축하 효과를 제공하는 패턴. |
| **UX 원칙** | **긍정적 강화 (Positive Reinforcement)** — B.F. Skinner의 조작적 조건형성. 바람직한 행동 후 보상을 제공하면 행동 반복이 촉진된다. **피크-엔드 법칙 (Peak-End Rule)** — Daniel Kahneman. 경험의 정점과 끝 부분이 전체 경험의 인상을 결정한다. 완료 순간에 축하 효과를 넣으면 긍정적 인상이 지속된다. |
| **플랫폼** | Both |
| **구현 복잡도** | Medium |
| **실제 사례** | Duolingo 레슨 완료 축하, GitHub 첫 PR 머지 컨페티, Notion 체크리스트 완료, Linear 이슈 완료 효과, 토스 목표 달성 |

**구현 팁:**
- `canvas-confetti` 라이브러리로 컨페티 효과 간편 구현
- Lottie 파일로 복잡한 축하 애니메이션 재생
- 효과는 1~3초 이내로 짧게, 화면 중앙이 아닌 완료 버튼 근처에서 발생
- 과도한 사용 금지 — 정말 의미 있는 성취에만 적용 (매일 로그인에 컨페티는 과함)
- `prefers-reduced-motion` 대응: 모션 대신 정적 배지나 축하 메시지로 대체

### 10.3 게이미피케이션 (Gamification / 게임화 요소)

| 항목 | 내용 |
|------|------|
| **설명** | 포인트, 뱃지, 레벨, 리더보드, 스트릭(연속 기록), 퀘스트 등 게임 메커니즘을 비게임 환경에 적용하는 패턴. |
| **UX 원칙** | **자기결정이론 (Self-Determination Theory)** — Deci & Ryan. 자율성(Autonomy), 유능감(Competence), 관계성(Relatedness) 3가지 내재적 동기가 충족되면 지속적 참여가 이루어진다. 게이미피케이션은 주로 유능감(레벨업)과 관계성(리더보드)에 작용. |
| **플랫폼** | Both |
| **구현 복잡도** | High |
| **실제 사례** | Duolingo (스트릭, XP, 리그), LinkedIn 프로필 완성도, GitHub Contributions 그래프, 토스 만보기, 삼성 헬스 뱃지 |

**구현 팁:**
- 진행 표시(프로그레스 바)로 "다음 레벨까지 얼마나 남았는지" 시각화
- 스트릭(연속 일수)은 강력한 동기이지만, 깨질 때 좌절감이 크므로 "프리즈" 기능 제공
- 리더보드는 상위권이 아닌 사용자에게 좌절감 유발 가능 — 친구 기준, 주간 리셋 등으로 완화
- 외재적 보상(포인트)만으로는 장기 참여 유지 어려움 — 내재적 동기(학습, 성장)와 연결 필수

### 10.4 개인화 경험 (Personalized Experience / 맞춤형 경험)

| 항목 | 내용 |
|------|------|
| **설명** | 사용자의 행동, 선호도, 위치, 시간 등을 기반으로 콘텐츠와 인터페이스를 맞춤화하는 패턴. |
| **UX 원칙** | **칵테일 파티 효과 (Cocktail Party Effect)** — 자신의 이름이나 관심사와 관련된 정보에 자동으로 주의가 집중된다. **자기 참조 효과 (Self-Reference Effect)** — 자신과 관련된 정보가 더 잘 기억된다. |
| **플랫폼** | Both |
| **구현 복잡도** | High |
| **실제 사례** | Spotify Discover Weekly, Netflix 맞춤 추천, YouTube 추천 알고리즘, 토스 맞춤 금융 상품, 쿠팡 개인화 홈 |

**구현 팁:**
- 이름으로 인사 ("안녕하세요, 김철수님"), 시간대별 인사 ("좋은 아침이에요")
- 사용 패턴 기반 바로가기: 자주 사용하는 기능을 상단에 배치
- 개인화의 이유를 투명하게 설명 ("이 상품을 본 사용자가 함께 구매한 제품")
- 개인화 해제/조정 옵션 제공 (사용자 통제감 유지)
- 개인정보 보호와 투명성 최우선 — GDPR, 개인정보보호법 준수

### 10.5 사운드 디자인 (Sound Design / 음향 디자인)

| 항목 | 내용 |
|------|------|
| **설명** | UI 인터랙션에 적절한 효과음을 결합하여 다중 감각적 경험을 제공하는 패턴. 알림음, 완료음, 에러음, 전환음 등. |
| **UX 원칙** | **다중 감각 강화 (Multisensory Enhancement)** — 시각+청각 결합 시 정보 인지 정확도와 반응 속도가 향상된다. **소닉 브랜딩 (Sonic Branding)** — 특정 소리가 브랜드와 연결되어 인식도와 감성적 연결을 강화 (예: Intel 사운드 로고, 카카오톡 알림음). |
| **플랫폼** | Both (모바일에서 더 적극적) |
| **구현 복잡도** | Medium |
| **실제 사례** | 카카오톡 메시지 알림음, 토스 송금 완료음, iOS 키보드 클릭음, Slack 알림음 "Knock Brush", Facebook Messenger 팝 효과음 |

**구현 팁:**
- 소리는 기본 OFF — 사용자가 원할 때만 활성화 (무음 모드 존중)
- 효과음은 100~500ms 이내의 짧고 경쾌한 소리
- 에러음은 불쾌하지 않으면서도 주의를 끌 수 있는 톤 (날카로운 소리 금지)
- Web Audio API 또는 Howler.js로 구현, 네트워크 지연 방지를 위해 사전 로드
- 반복되는 인터랙션(키보드 입력 등)은 소리 볼륨을 낮추거나 변화를 주어 피로 방지

## 11. 다크 패턴 — 피해야 할 것들 (Dark Patterns to Avoid)

다크 패턴(Deceptive Patterns)은 사용자를 속이거나 의도하지 않은 행동을 하도록 유도하는 사기적 디자인 기법이다. Harry Brignull이 2010년 처음 명명했으며, EU의 디지털 서비스법(DSA), 미국 FTC, 한국 공정거래위원회에서 점차 규제를 강화하고 있다. 단기적 비즈니스 지표를 올릴 수 있으나 장기적으로 사용자 신뢰를 파괴하고 법적 리스크를 초래한다.

### 11.1 확인 수치심 (Confirmshaming / 죄책감 유발 선택지)

| 항목 | 내용 |
|------|------|
| **설명** | 거부 선택지를 죄책감을 느끼게 하는 문구로 작성하여 수락을 유도하는 패턴. |
| **왜 나쁜가** | 사용자의 자율적 의사결정을 감정적으로 조작한다. 단기적으로 클릭률을 올리지만 브랜드에 대한 반감과 불신을 축적시킨다. |
| **실제 사례** | "아니요, 할인 혜택을 포기하겠습니다", "저는 건강에 관심이 없습니다", "아니요, 돈을 절약하고 싶지 않습니다" |

**올바른 대안:**
- 거절 선택지는 중립적 문구 사용: "괜찮아요, 다음에 할게요" / "나중에 결정하기"
- 수락과 거절 버튼의 시각적 무게를 균등하게 (크기, 색상, 위치)

### 11.2 강제 연속 (Forced Continuity / 자동 갱신 함정)

| 항목 | 내용 |
|------|------|
| **설명** | 무료 체험 종료 후 명확한 통지 없이 자동으로 유료 구독으로 전환하는 패턴. 해지 절차를 의도적으로 복잡하게 만드는 것도 포함. |
| **왜 나쁜가** | 사용자의 명시적 동의 없이 결제가 발생하여 경제적 피해를 준다. 한국 전자상거래법, EU 소비자 보호법에서 명시적으로 금지하거나 규제하는 행위. |
| **실제 사례** | 무료 체험 시 카드 등록 → 알림 없이 유료 전환, 해지 버튼을 깊은 설정 메뉴에 숨김, 해지 시 전화 필수 요구 |

**올바른 대안:**
- 체험 종료 3일, 1일 전 이메일/앱 알림으로 유료 전환 사전 고지
- 구독 해지는 가입만큼 쉽게 — 설정에서 2클릭 이내 해지 가능
- "구독을 해지하시겠습니까?" → "네, 해지합니다" / "계속 유지합니다" 명확한 선택지
- 해지 후에도 남은 기간까지 서비스 이용 가능하도록

### 11.3 트릭 질문 (Trick Questions / 혼동 유도 질문)

| 항목 | 내용 |
|------|------|
| **설명** | 이중 부정, 혼란스러운 문구, 체크박스의 의미 뒤집기 등으로 사용자가 의도와 반대 선택을 하도록 유도하는 패턴. |
| **왜 나쁜가** | 사용자의 인지적 취약점(빠른 스캔, 패턴 기반 판단)을 악용한다. 정보의 명확성(Clarity)이라는 기본 디자인 원칙에 위배. |
| **실제 사례** | "마케팅 이메일을 받지 않으려면 체크를 해제하지 마세요" (이중 부정), 체크박스의 의미가 항목마다 반대 (체크=동의 vs 체크=거부 혼재) |

**올바른 대안:**
- 단순하고 긍정적인 문장: "마케팅 이메일을 받겠습니다" (체크=동의)
- 모든 체크박스의 의미 방향을 일관되게 유지 (체크=동의로 통일)
- 이중 부정 금지 — 한 번 읽어서 의미가 즉시 파악되어야 함

### 11.4 숨겨진 비용 (Hidden Costs / 결제 직전 추가 비용)

| 항목 | 내용 |
|------|------|
| **설명** | 결제 마지막 단계에서 이전에 공개되지 않았던 수수료, 배송비, 서비스 요금 등이 갑자기 추가되는 패턴. |
| **왜 나쁜가** | 가격 투명성에 대한 신뢰를 완전히 파괴한다. 매출은 일시적으로 발생하지만 장바구니 포기율(Cart Abandonment Rate)이 급증한다. Baymard Institute 연구에 따르면 예상치 못한 추가 비용이 장바구니 포기의 1위 원인(48%). |
| **실제 사례** | 항공권 검색 시 표시 가격에 세금·수수료 미포함, 배송비가 결제 단계에서만 표시, 서비스 이용료·처리 수수료의 갑작스러운 추가 |

**올바른 대안:**
- 상품 목록 단계부터 총 비용(배송비 포함) 표시
- 세금·수수료가 별도인 경우 상품 가격 옆에 "별도"를 명시
- 장바구니에서 비용 내역(상품가 + 배송비 + 세금) 항목별 투명하게 표시
- 무료 배송 기준 금액을 명확히 안내

### 11.5 방해 광고/강제 행동 (Roach Motel / 진입은 쉽고 탈출은 어려운)

| 항목 | 내용 |
|------|------|
| **설명** | 가입·구독·동의는 매우 쉽게 만들면서 해지·탈퇴·취소는 의도적으로 어렵게 만드는 비대칭적 설계 패턴. |
| **왜 나쁜가** | 사용자의 선택의 자유를 구조적으로 제한한다. "탈퇴가 어려우니 계속 쓰겠지"라는 가정은 단기적이며, 장기적으로 네거티브 리뷰, 규제 기관 신고, 소송으로 이어진다. |
| **실제 사례** | 이메일 구독은 1클릭이지만 해지는 로그인 필요, 계정 삭제를 고객센터 전화/메일로만 가능하게 함, 구독 해지 시 여러 단계의 "정말요?" 확인 질문 연속 |

**올바른 대안:**
- **대칭적 설계**: 가입이 3단계면 해지도 3단계 이하
- 탈퇴/해지 링크를 설정 페이지에서 바로 접근 가능하게 배치
- 이메일 하단의 "수신 거부" 링크는 1클릭으로 즉시 처리
- 해지 사유를 물어볼 수는 있지만 필수가 아닌 선택 사항으로

### 11.6 시각적 간섭 (Visual Interference / 눈속임)

| 항목 | 내용 |
|------|------|
| **설명** | 시각적 디자인으로 특정 선택지를 강조하거나 다른 선택지를 눈에 띄지 않게 만드는 패턴. 큰 "동의" 버튼 vs 작은 회색 "거부" 링크 등. |
| **왜 나쁜가** | 형식적으로는 선택지가 존재하지만, 시각적 계층 구조를 조작하여 실질적 선택의 자유를 제한한다. 특히 개인정보 동의, 마케팅 수신 동의 등에서 악용 시 법적 문제. |
| **실제 사례** | "동의" 버튼은 크고 파란색, "거부" 버튼은 작은 회색 텍스트 링크, 쿠키 동의 배너에서 "모두 수락"만 버튼, "설정 관리"는 텍스트 링크 |

**올바른 대안:**
- 동의/거부 버튼의 시각적 무게(크기, 색상, 위치)를 균등하게
- 쿠키 배너: "모두 수락" / "모두 거부" / "설정 관리" 3가지를 동일한 시각적 무게로
- 중요한 선택일수록(개인정보, 결제) 선택지 간 시각적 차이를 줄여야 함

### 11.7 강제 행동 (Forced Action / 원치 않는 행동 요구)

| 항목 | 내용 |
|------|------|
| **설명** | 원하는 기능을 사용하기 위해 관련 없는 행동(앱 평가, 소셜 공유, 연락처 접근 허용 등)을 강제하는 패턴. |
| **왜 나쁜가** | 사용자의 자율성을 침해하고, 강제된 행동(예: 별 5개 평가)은 데이터의 신뢰성도 훼손한다. Apple App Store와 Google Play Store 모두 리뷰 강제를 금지하고 있다. |
| **실제 사례** | "앱을 평가하지 않으면 이 기능을 사용할 수 없습니다", "친구 5명을 초대해야 잠금 해제", 핵심 기능 사용 시 불필요한 개인정보 수집 강제 |

**올바른 대안:**
- 평가 요청은 적절한 시점에 정중하게, 그리고 거절 시 다시 묻지 않기 (또는 장기간 후 1회만)
- 선택적 공유: 공유하면 보너스, 하지 않아도 기본 기능은 완전히 사용 가능
- 데이터 수집은 최소 필요 범위만, 수집 사유를 투명하게 설명

## 부록: UX 원칙 요약 사전

| 원칙 | 설명 | 제안자/출처 |
|------|------|-------------|
| **피츠의 법칙 (Fitts's Law)** | 타겟까지 이동 시간은 거리에 비례하고 크기에 반비례한다 | Paul Fitts (1954) |
| **힉의 법칙 (Hick's Law)** | 선택지가 많을수록 결정 시간이 로그 함수적으로 증가한다 | William Hick (1952) |
| **야콥의 법칙 (Jakob's Law)** | 사용자는 다른 사이트에서의 경험을 기반으로 디자인을 기대한다 | Jakob Nielsen |
| **밀러의 법칙 (Miller's Law)** | 인간의 작업 기억은 한 번에 7±2개 항목을 처리한다 | George Miller (1956) |
| **도허티 임계값 (Doherty Threshold)** | 시스템 응답이 400ms 이내일 때 생산성이 급격히 향상된다 | Walter Doherty (1982) |
| **목표 구배 효과 (Goal-Gradient Effect)** | 목표에 가까워질수록 노력을 높인다 | Clark Hull (1932) |
| **피크-엔드 법칙 (Peak-End Rule)** | 경험의 정점과 끝이 전체 인상을 결정한다 | Daniel Kahneman |
| **폰 레스토프 효과 (Von Restorff Effect)** | 유사한 항목들 중 눈에 띄는 것이 더 잘 기억된다 | Hedwig von Restorff (1933) |
| **자이가르닉 효과 (Zeigarnik Effect)** | 미완료 과제가 완료된 과제보다 더 잘 기억된다 | Bluma Zeigarnik (1927) |
| **심미적 사용성 효과 (Aesthetic-Usability Effect)** | 미적으로 아름다운 디자인이 더 사용하기 쉽다고 인식된다 | Masaaki Kurosu & Kaori Kashimura (1995) |
| **테슬러의 법칙 (Tesler's Law)** | 모든 프로세스에는 줄일 수 없는 최소한의 복잡성이 존재한다 | Larry Tesler |
| **직렬 위치 효과 (Serial Position Effect)** | 목록의 첫 번째와 마지막 항목이 가장 잘 기억된다 | Hermann Ebbinghaus (1885) |
| **인지 부하 이론 (Cognitive Load Theory)** | 인지 자원은 한정적이므로 불필요한 부하를 최소화해야 한다 | John Sweller (1988) |
