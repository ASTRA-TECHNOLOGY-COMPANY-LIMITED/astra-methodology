# 사람처럼 쓰기 — 규칙 정본

기준은 하나다. **옆자리 동료에게 소리 내어 말했을 때 어색하면 고쳐 쓴다.**
격식 차린 보고서체도, 기계 번역체도 아니다 — 일 잘하는 동료가 말로 설명해 주는 문장을 쓴다.

이 문서가 규칙의 정본이고, 같은 폴더의 `check-korean-style.py` 가 그중 기계로 판정할 수 있는
부분을 옮긴 것이다. 둘 중 하나만 고치지 않는다.

## 검사기와 사람이 나눠 맡는 것

검사기는 **어휘·형태의 티**만 본다. 정규식으로 셀 수 있는 것뿐이다.
아래 넷은 기계가 못 본다 — 글을 쓰는 쪽이 직접 챙긴다.

**결론 먼저.** 무엇을 조사했고 어떻게 검증했는지로 답을 시작하지 않는다. 답부터 말하고 근거는
필요한 만큼만 붙인다.

**낯선 개념은 아는 것에 빗대 한 문장으로 세운 다음** 이름을 붙인다. "PDF는 두 종류다 — 워드로
만든 것은 글자가 글자로 들어 있고, 스캔한 것은 사진 한 장이다"를 먼저 깔고 나서 '텍스트 레이어'라는
말을 꺼낸다. 전문 용어를 쓸 거면 처음 나올 때 괄호로 푼다. 풀어쓰기 어색하면 그 용어가 정말
필요한지 의심한다.

**표는 정말 격자 데이터일 때만.** 항목이 서넛이면 문단으로 말하는 게 더 빨리 읽힌다. 표가 세 개를
넘어가면 문서가 아니라 자료 덤프다. 짧은 답은 문단으로 말한다 — 헤더·불릿은 내용이 실제로
열거나 구조일 때만 쓴다.

**"어렵다"는 말이 나오면 설명을 늘리지 말고 다시 쓴다.** 같은 내용을 더 길게 풀면 더 어려워진다.
비유 하나 세우고 문단으로 재작성한다.

## 규칙표

심각도 셋이다. **S1** 은 반려(exit 2), **S2** 는 누적되면 경고(exit 1), **S3** 은 참고다.
임계는 "이 횟수를 넘겨야 계상한다"는 뜻이다 — 0 이면 한 번만 나와도 잡고, 1 이면 두 번째부터 잡는다.

### 번역투 T

| ID | 심각도 | 임계 | 잡는 것 | 고치는 법 |
| --- | --- | --- | --- | --- |
| T1 | S2 | 1 | ~에 대해(서) · ~에 대한 · ~에 관해 | 목적격 조사로 직결. "제도에 대해 설명한다" → "제도를 설명한다" |
| T2 | S1 | 0 | ~에 있어서 | "~에서" 또는 "~할 때" |
| T3 | S1 | 0 | 이중 피동 (되어지다·보여지다·잊혀지다·쓰여지다·불려지다·모아지다) | 단순 피동으로. "판단되어진다" → "판단한다" |
| T4 | S1 | 0 | ~을 가지고 있다 | 동사로. "강점을 가지고 있다" → "강점이 있다" |
| T5 | S2 | 0 | ~에 의해 + 피동 | 능동으로. "법에 의해 정해진다" → "법이 정한다" |
| T6 | S2 | 0 | 이중 조사 (에서의·으로의·로의·에의·로부터의) | 절로 푼다. "현지에서의 생활" → "현지 생활" |
| T7 | S2 | 2 | ~를 통해 반복 | 3회를 넘으면 일부를 "~로"·"~해서"로 분산 |
| T8 | S2 | 1 | ~라는 점에서 반복 | "~라서"·"~니까" |
| T9 | S3 | 2 | 인칭 대명사 밀도 (그·그녀·그들·그것) | 생략하거나 이름·호칭으로 |

`~에 관한`은 일부러 뺐다 — "개인정보 보호에 관한 법률"이 법령 제목의 표준 형식이다.

T1 이 S1 이 아닌 이유: 짧은 카피에서는 반려감이지만 긴 문서에서는 "변수에 대한 집중 관리"처럼
고칠 값어치는 있어도 글을 막을 정도는 아닌 용례가 대부분이다. 신호는 존재가 아니라 반복이다.

### 명사화·격식 과잉 N

| ID | 심각도 | 임계 | 잡는 것 | 고치는 법 |
| --- | --- | --- | --- | --- |
| N1 | S2 | 0 | 명사화 동사 — "삭제 작업을 수행합니다" | 동사로 되돌린다. → "삭제합니다" |
| N2 | S2 | 1 | ~하기 위해 · ~하기 위한 | "~하려고"·"~하려면". 관형형은 "~할"로 — "조회하기 위한 조건" → "조회할 조건" |
| N3 | S1 | 0 | ~하도록 하겠습니다 | 한 겹으로. "정리해 드리도록 하겠습니다" → "정리하겠습니다" |
| N4 | S2 | 0 | 딱딱한 한자어 (상기 내용·금번·제반·소정의·상이하다·기입) | 위 내용, 이번, 다르다, 적기 |
| N5 | S3 | 3 | '해당' 반복 | 대부분 "그" 또는 생략으로 통한다 |

N1 의 목록은 닫힌 기술 용어만 담는다. 열린 명사를 넣으면 "회의를 진행합니다" 같은 정상 문장을
먹는다 — 회의는 동사가 아니라 사건이다.

N3 은 `하겠` 계열만 잡는다. "늦지 않도록 하자"나 규격서의 "~하도록 한다"는 정상 문형이다.

### AI 관용구 D

| ID | 심각도 | 임계 | 잡는 것 | 고치는 법 |
| --- | --- | --- | --- | --- |
| D1 | S1 | 0 | 상투적 도입·결말어 (결론적으로·요컨대·종합하면·정리하면) | 삭제. 답은 첫 문장에서 말한다 |
| D2 | S1 | 0 | 의의 과장 (시사하는 바가 크다·주목된다·귀추가 주목) | 무엇이 왜 그런지로 바꾸거나 삭제 |
| D3 | S1 | 0 | 훈계형 — 고정 관용구·청자 높임 (~할 필요가 있다·~하는 것이 중요하다·~하셔야 할 것이다·명심해야) | "확인할 필요가 있다" → "확인하자" |
| D3b | S2 | 0 | ~야 할 것이다 (높임 없는 형태) | 남에게 시키는 말이면 "지키자"로. 전망이면 그대로 둔다 |
| D4 | S2 | 1 | 완곡 회피 (~라고 할 수 있다·~인 셈이다·~것으로 보인다) | 단정할 수 있으면 단정한다 |
| D5 | S2 | 0 | 과장 수식 (혁신적·획기적·게임 체인저·최적의 솔루션) | 삭제. 강조는 수식어가 아니라 숫자로 |
| D6 | S2 | 1 | 뜻 없는 수식어 (매우·굉장히·효과적으로·원활하게·성공적으로·다양한) | 삭제 |
| D7 | S2 | 0 | 공허한 수사 (시대의 흐름 속·균형점을 찾·화두로 떠오르) | 구체적 사실·숫자로 바꾸거나 삭제 |

D2 의 관형형은 **뒤에 오는 명사로 갈린다.** "주목받는 변화"(추상어)는 슬롭이고 "주목받는
기업"(구체 명사)은 사실 서술이다. 그냥 넓혔더니 정상 문장이 반려됐다(실측 5건).

D3 을 둘로 나눈 이유가 이 문서에서 가장 중요한 대목이다. **심각도는 그 패턴이 실제로 판별할
수 있는 만큼만 준다.**

"기한을 지켜야 할 것이다"(훈계)와 "내년에는 시스템을 바꿔야 할 것이다"(전망)는 같은 형태다.
갈리는 건 용언도 주어도 아니고 **화행** — 누구에게 하는 말인가 — 인데, 그건 문장 어디에도 표지가
없다. 뒤(용언)를 묶어 봤더니 전망·조건절 귀결 7종이 전부 차단됐다(실측 7/7). 그래서 이 갈래는
S2 다. 리포트와 설계 문서는 전망을 쓰는 장르라 차단하면 글이 막힌다.

반대로 D3 에 남긴 것들은 문장 안에 근거가 있다. 고정 관용구이거나, 청자 높임 `~셔야`가 문법
표지로 대상을 독자에 못박는다. 오탐 위험이 없어 차단해도 된다.

둘 다 1인칭 주어가 앞에 오면 면제된다 — 화자 자신의 의지다.

### 구조·리듬 C

| ID | 심각도 | 임계 | 잡는 것 | 고치는 법 |
| --- | --- | --- | --- | --- |
| C1 | S1 | 0 | 연결어미 뒤 쉼표 | 쉼표를 뺀다 (표 아래 예시) |
| C2 | S2 | 0 | 부정 대구 "A가 아니라 B" (2회 이상이면 S1) | 그냥 B라고 쓴다 |
| C3 | S2 | 0 | 3항 나열 (대등 용언) | 정말 셋일 때만 셋. 대개 하나면 된다 |
| C4 | 표면별 | — | 이모지 한도 초과 | 표면 한도를 지킨다 |
| C5 | S2 | — | 같은 종결어미 4연속 | 종결을 섞는다 |
| C6 | S2 | 0 | 기계적 3단 (먼저…다음으로…마지막으로) | 순서가 진짜 중요할 때만 |

C1 은 한국어 AI 글을 가려내는 **가장 값싸고 강한 신호**다(KatFishNet 기반 실측 4.84배 분리도).
그래서 S1 이다. 명사 '이해도'의 도를 연결어미로 읽는 오탐만 앞말로 뺐다.

```text
쓰지 않는다:  기술은 빠르게 발전하지만, 조직은 더디다.
대신:        기술은 빠르게 발전하지만 조직은 더디다.
```

이 예시들은 코드펜스 안에 둔다 — 규칙책이 나쁜 형태를 인용해야 하는데 그대로 본문에 두면
검사기가 자기 규칙책을 반려한다.

C3 은 용언 3연속만 잡는다. 명사 나열("여권, 비자, 계약서")은 체크리스트의 기본 문형이다.

한둘은 남긴다.

## 표면

같은 규칙이라도 글의 종류에 따라 맞지 않는 것이 있다. 완화는 **오직 `off` 목록으로만** 한다 —
검사기의 `SURFACE_CFG` 와 이 표가 정확히 같아야 한다.

| 표면 | 쓰는 곳 | 이모지 | 끄는 규칙 |
| --- | --- | --- | --- |
| `doc` | 설계·기획 문서, 매뉴얼, README | 2 | C6 |
| `proposal` | 제안서 본문 HTML | 0 | C5 · C6 · T9 |
| `report` | 분석 리포트 (리스크·사업성·FP) | 1 | C5 · C6 |
| `hitl` | 사용자에게 던지는 질문 | 0 | C3 · C5 · C6 · T9 |
| `chat` | 세션 응답 | 0 | C5 · T9 |
| `comment` | 코드 주석 · 커밋 메시지 · PR 본문 | 0 | C3 · C5 · C6 · T9 · D4 · E2 |

`doc` 에서 C6 을 끄는 이유는 절차 문서에서 "먼저…다음으로…마지막으로"가 정상 문형이라서다.
`proposal` 에서 C5 를 끄는 이유는 격식 존댓말에서 '~니다' 연속이 규범이라서다. **어휘 티(T·D·N·A)는
어느 표면에서도 끄지 않는다** — 격식체와 번역투는 다른 축이다.

## 돌리는 법

```bash
CHK="${CLAUDE_PLUGIN_ROOT}/skills/korean-style/references/check-korean-style.py"

python3 "$CHK" --surface doc docs/blueprints/auth.md
python3 "$CHK" --surface proposal --kind html data/output/사업명/1-1.html
cat answer.txt | python3 "$CHK" --surface chat -

python3 "$CHK" --selftest        # 규칙을 고쳤으면 반드시
```

`--kind` 는 확장자로 자동 결정된다(`auto`). 마크다운은 코드펜스를, HTML 은 태그를, 코드 파일은
주석 밖을 검사에서 뺀다. `--min-hangul 0.3` 을 주면 한글 비율이 낮은 파일은 건너뛴다.

exit **0** 통과 / **1** 경고 / **2** 반려 / **3** 실행 오류.

> `| head` 를 덧붙이지 않는다. `$?` 가 검사기가 아니라 `head` 의 것이 되어, S1 이 여섯 건인
> FAIL 이 `0` 으로 보인다(실측). 명령 치환(`$(...)`)도 같은 함정이다.

## 고칠 때의 원칙

**빼기만 한다.** AI 티를 지우려다 원문에 없던 비유·상투구("기록적인 성과를 거두었다"·"~로
평가된다")를 새로 심지 않는다. 넣는 순간 그게 새 AI 티다.

**검사기 판정이 정본이다.** 자가 판단으로 덮어쓰지 않는다 — 자가 평가는 언제나 통과한다.
S1 은 예외 없이 고친 뒤 다시 돌린다. exit 3 도 통과가 아니다. 경로를 고쳐 다시 돌리고,
그래도 못 돌리면 "문체 미검증"이라고 밝힌다.

**문장 길이에 리듬을 준다.** 같은 길이의 문장이 이어지면 기계 낭독처럼 들린다.

**볼드는 한 화면에 몇 개만.** 접속부사(또한·게다가·따라서)로 문장을 계속 잇지 않는다 — 대부분
빼도 통한다. "결론적으로 / 정리하면"으로 이미 한 말을 반복하지 않는다.

## 손대지 않는 것

**남의 말을 옮긴 구간.** 출처가 밝혀진 큰따옴표 직접 인용은 점수·판정에서 뺀다. 고치는 것 자체가
왜곡이기 때문이다. 다만 면제는 **조용한 통과가 되지 못한다** — 검사기는 출처가 진짜인지 모르므로
판정이 최소 WARN 으로 바닥 처리돼 사람 눈에 올라간다.

출처로 인정하는 것은 URL, 법령·문서·기관 이름, "X에 따르면", "제안요청서 3.2절" 뿐이다.
"그가 말했다"·"자료에 따르면" 같은 서사 어휘는 인정하지 않는다 — 지어낸 슬롭 앞에 붙이기가
진짜 인용 앞에 붙이기보다 쉬워서, 두 단어짜리 우회로가 된다(실측).

**코드·태그·수치.** 코드펜스 안, HTML 태그, URL, 숫자, 영문 식별자는 검사하지 않는다.
**인라인 백틱은 예외로 검사한다** — 백틱을 가렸더니 그 안이 슬롭 은신처가 됐다(실측).

## 규칙을 고칠 때

두 가지가 반복해서 확인됐다. 규칙을 손대기 전에 읽는다.

**넓은 구간 면제는 형태를 바꿔도 우회로가 된다.** 인용 마스크, 코드펜스 마스크, 화이트리스트 —
셋 다 같은 방식으로 뚫렸다. 마지막 사고는 화이트리스트에 30자짜리 1인칭 패턴을 넣은 것이다.
"나도" 두 글자를 앞에 붙이면 그 뒤 30자 안의 T1·D1·D6·T3 가 전부 빠졌다. 면제가 필요하면
**그 규칙 안으로만** 넣는다(D3 의 `FIRST_PERSON_LEAD` 후처리가 그 형태다). 화이트리스트
항목은 8자 이하로 유지한다.

**확장은 어미로 하고 어휘로 하지 않는다.** 뒤에 오는 말로 판정하는 축(D2 의 추상어, N1 의
경동사)은 안전하게 묶을 수 있다. 앞에 오는 말로 판정하는 축은 넓히는 순간 오탐이 100%가 된다.
반대로 앞말로 **빼는** 것은 안전하다 — C1 의 `이해도` 제외가 그 형태다.

**판별 근거가 문장 밖에 있으면 심각도를 내린다.** 규칙을 어느 방향으로 묶어도 안 되는 축이
있다. D3b 의 `~야 할 것이다`가 그렇다 — 훈계인지 전망인지는 화행에 달렸고 문장 안에 표지가
없다. 뒤를 묶었더니 오탐이 7/7 로 늘었다. 이럴 때 규칙을 더 깎지 말고 **S1 을 S2 로 내린다.**
못 갈리는 것을 차단하면 정상 문장이 막히고, 경고로 두면 사람이 판단한다.

**셀프테스트는 규칙 ID 까지 본다.** exit 코드만 맞추면 정규식이 죽어도 다른 규칙이 대신 걸려
통과한다(실측: 죽은 정규식 셋이 그렇게 살아남았다). 픽스처의 빈 튜플은 "아무것도 걸리면 안 된다"는
오탐 가드다.
